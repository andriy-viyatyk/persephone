# QA run — EPIC-099: the agent event channel

**Date:** 2026-09-08
**Build:** `upcoming-v5.0.1`, dev app, `ai-vision@1.1.0`
**Surface:** [qa/surfaces/events.md](../surfaces/events.md)
**Epic:** [EPIC-099](../../doc/epics/EPIC-099.md) (US-1397 … US-1400)

Two halves: a mechanical run over MCP `call`, and the weak-agent walkthrough. Both were run
against the live dev app; nothing here is inferred from the code.

## Test surfaces used

- Board: `C:\projects\test-boards\aivision-probe`, the EPIC-097 scratch board. One line was added
  to its `app.js` for this run — `window.__probeRemote = window.persephone.aiVision.expose(model)`
  instead of discarding the handle — so `refresh()` and `notify()` can be called on demand. It is
  additive and left in place; the board is a test fixture and the handle makes it a better one.
- Web page: `C:\projects\ai-vision\examples\demo-page\index.html` from `file://`.
- Second and third MCP sessions: a throwaway Node client against `http://127.0.0.1:7865/mcp`
  (`initialize`, then one `tools/call` per path). Necessary because the cursor is per session and
  every subagent in one Claude Code process shares that process's session.
- Stand-in user: for a press that must land *while* a `step` is blocked, a `setInterval` in the
  **main** process driving `webContents.executeJavaScript` — not queued behind the blocked renderer
  call, unlike anything sent over MCP.

## Part 1 — mechanical

### E.1 — an event reaches a session that did not cause it, once — **PASS**

Session A reloaded the probe board. A fresh session's first call carried:

```
--- events ---
Events since your last call:
  [seq 3] The board reloaded; re-read pages["98f8ee76-…"].editor.app.
--- end events ---
```

Its second call to the same path carried no block. Session A also saw the event it caused, which is
correct: per-session cursors mean the causing session has not seen it either.

### E.2 — independent unseen sets, newest three, `+N` counts unseen only — **PASS**

With five events in the ring, all already consumed by session A, a brand-new session's first call
returned:

```
Events since your last call:
  [seq 3] The board reloaded; re-read pages["98f8ee76-…"].editor.app.
  [seq 4] The board shape changed; re-read pages["98f8ee76-…"].editor.app.
  [seq 5] the user picked the second item. (written by the board, not by persephone)
+2 earlier events; read events.recent().
```

The **newest** three in full (the confirmed decision, not the oldest three), the older two counted,
and `+2` counting only what that session had not seen. Session A received nothing.

### E.3 — `recent` / `since` / `count` agree with the ring — **PASS**

In one fresh session: `count` → `5`; `since(3)` → seq 4 then 5, oldest first, excluding 3;
`recent(2)` → seq 5 then 4, newest first. Every entry carried `seq`, `time`, `kind`, `text`,
`origin`, and `path`.

### E.4 — `wait` — **PASS**, and it caught a real defect before shipping

- `events.wait(3000)` → `{ pending: true, waitedMs: 3013 }`.
- `events.wait(25000)` in a second session, with a board `notify()` fired from the first ~5 s later
  → `{ pending: false, waitedMs: 5297, event: { seq: 6, kind: "remote-notify", … } }`, and the same
  entry in that result's `events` block.
- `events.wait(40000)` → `{ pending: true, waitedMs: 40014 }`.

The 40 s case is the one that matters. `sendToRenderer` defaults to a 30 s bridge timeout and
`call-tools.ts` was not passing an override, so before the fix a 50 s wait would have come back as
a `Request timeout` **error** rather than `{ pending: true }` — the design's central promise,
broken by Persephone's own plumbing rather than by any client. Blocking paths now get 125 s, and
the ordering `renderer bound (50 s / 110 s) < bridge (125 s) < client timeout` is the invariant.
This was found during plan review, not during the run; the run is what proved the fix.

### E.5 — remote shape signals, and the proxy serving the new shape — **PASS**

- Browser page: `typeof window.__aiVisionHostSignal` in the probed demo page is `"function"` — the
  CDP `Runtime.addBinding` path is live. `window.__aiVision.refresh()` produced
  `[seq 1] The browser page's shape changed; re-read pages["8c73…"].editor.app.` and a following
  read of `page.editor.app.filterStatus` returned `all`.
- Board: `window.__probeRemote.refresh()` produced `[seq 4] The board shape changed; …`, and
  `page.editor.reload()` produced `[seq 3] The board reloaded; …`.
- Both shape entries carry `origin: "persephone"` and no attribution suffix.

### E.6 — attribution — **PASS**, after a defect found here

A board `notify("the user picked   the second\n item")` produced
`[seq 5] the user picked the second item. (written by the board, not by persephone)` with
`origin: "board"` and the whitespace collapsed. A page `notify()` produced the same with
`origin: "page"`.

**Defect found and fixed during this run:** the first implementation stamped the *host-written*
`shape-changed` sentence with the remote's origin, so a line Persephone composed was rendered as
"(written by the page, not by persephone)". The label exists to mark prose an untrusted remote
wrote; applying it to host text teaches an agent that the label is noise, which is worse than not
having it. Only `remote-notify` now carries a remote origin.

**Second defect found and fixed during this run:** `refresh()` immediately followed by `notify()` —
the normal case, a page changing its model and saying why — lost the notify. The shape branch
re-probes, which clears the live registration, and the notify guard required one. The notify guard
now uses the *historical* "this tab has registered a model" set, which keeps the anti-injection
property (the binding exists on every browser page, including pages that never called `expose()`)
without the race.

### E.7 — `ui.guide.step` — **PASS**, after two defects found here

- Press while blocked: with a main-process stand-in user clicking 6 s in,
  `ui.guide.step("mcp-indicator", "…", { timeoutMs: 30000 })` returned
  `{ pressed: "Skip", target: "mcp-indicator" }`.
- Press after a `pending`: `step(… { timeoutMs: 3000 })` → `pending`; a
  `window.screen.click("[data-name=\"ai-vision-highlight-button-next\"]")` logged the press; the
  retry returned `{ pressed: "Next" }` immediately, without redrawing.
- A control outside the shell: `ui.guide.step("[data-name=\"settings-section-theme\"]", …)` drew on
  the Settings section and returned the press.
- `ui.guide.end()` → `{ ended: true }`.
- `window.screen.click` addresses the overlay buttons by their `data-name` directly; no snapshot ref
  is needed.

**Defects found and fixed here:**

1. *A press with no active wait was discarded.* After a `pending` the card is still on screen; the
   user presses Next; nothing was recorded, because `onButton` only logged while a wait was active.
   The press is a fact about the user and must be recorded once regardless of whether anything
   happens to be blocked — the log is what a *second* session, or the same session after a
   `pending`, reads.
2. *A retry re-asked a question already answered.* Even with the press recorded, the retry drew a
   fresh card and blocked for another 50 s. It now consumes an unconsumed press for that target,
   guarded by a step id this guide issued, so a stale answer can never be replayed against a later
   question. Without both fixes together, the walkthrough loop is unusable by exactly the kind of
   model it was designed for.

## Part 2 — the weak agent

`mcp-test-agent-call` (Haiku, `call` as its only tool, no knowledge of Persephone). Prompt, in the
user's words:

> Walk me through the Persephone Settings page. Show me three controls, one at a time, and wait for
> me to press Next before moving to the next one.

A stand-in user pressed **Next** four seconds after each card appeared.

### Iteration 1 — **FAIL**

Route taken, in order:

1. `call` with no path (the overview)
2. `helpSearch("settings page")`
3. `pages.showSettingsPage()`
4. `settings.sections`
5. `settings.highlight("theme")`

Then it ended its turn and asked the user to type "Next" in chat. Asked afterwards what it had seen
that could point at a control *and wait*, it named `pages.logView.push` — the question-asking
channel — and said it had not implemented any UI interaction. It never visited `ui`.

Two distinct causes, and the more serious one was not prose:

- **A capability gap.** `ui.guide.step` resolved names only against the eight curated header
  controls. Even if the agent had found it, it could not have pointed at a Settings section. A
  walkthrough restricted to the window chrome is not a walkthrough. `step` now takes a **target**:
  a curated shell name, a CSS selector, or a bare `data-name` — and every addressable control in
  the app already publishes a resolved selector through its owning node's `elements`, per the
  UI-element contract.
- **A discoverability gap.** The guide's own prose was good, but it lived on `ui`, and the route a
  "walk me through the Settings page" request actually takes never passes through `ui`. Three
  edits, on the route the agent took: a line in the root overview's **Common paths** block (every
  session reads that on its first call); the third case in the root `ui` summary, beside the
  existing WHERE and SHOW cases; and one sentence in the `settings` node's help, where this agent
  stopped — `highlight` points and returns, `ui.guide.step` points and waits.

### Iteration 2 — **PASS**

Fourteen calls. It found `ui.guide.step` and used it once per control, waiting each time:

```
[seq 2] The user pressed "Next" on the guided step for "settings-section-theme".
[seq 3] The user pressed "Next" on the guided step for "settings-section-window-behavior".
[seq 4] The user pressed "Next" on the guided step for "settings-section-browser-profiles".
```

Seven seconds apart, which is the stand-in user's four-second delay plus the agent's own turn — the
calls genuinely blocked. It passed bare `data-name` values, the third of the three accepted target
forms, and then reported the three sections back to the user in its own words.

**Residual observation, not a failure.** It discovered the section names by running
`script.execute()` over the DOM for `[data-name]` attributes rather than reading
`settings.elements`, which lists the same names with a purpose line and a resolved selector. The
answer was right and the walkthrough worked, so the gate passes; but a weak agent reaching for
arbitrary renderer code where a curated, self-describing list already exists is worth watching. If
it recurs on another surface, the fix is on the `elements` side — making the curated list the
obvious first stop — not on `script.execute`.

No third iteration was needed.

---

## Verdict

**PASS.** Every mechanical scenario behaves as designed, and a Haiku agent with only the `call`
tool drove a three-step guided walkthrough of a screen it had never seen, from the overview and
hints alone.

Five defects were found and fixed before this run was recorded: the bridge timeout that would have
turned every long poll into an error, a session cursor left ahead of a restarted log (which would
have deafened a session permanently and silently), attribution applied to host-written text, a
notify lost to its own refresh, and the press/retry pair in `ui.guide`. Four of the five were only
visible from the outside — which is the argument for running the surface rather than reading the
diff.
