## Part 1 — mechanical verification

Driven by the implementing agent over MCP `call` against the running dev app.

### M.1 — `.app` resolves and describes itself

`pages[id].editor.app` returned the board's `summarize()` — `{ kind: "TodoApp", fileName:
"epic-098.todo.json", lists: 2, tags: 1, items: 3, shown: 3, selectedList: "", selectedTag: "",
searchText: "" }` — with a hint listing all 21 declared members plus `elements` and `highlight`.
`$help` added the `overview` block and the long-form help. Nothing about the board is reachable
only by reading its source.

### M.2 — collections and indexed hops

- `app.items` → the filtered, ordered array of item summaries; hint headed `TodoItems`.
- `app.items[0]` → the *item's* own shape (`TodoItem`, eight members).
- `app.items["<uuid>"]` → the same item by id — the string index is the item id, as its summary says.
- `app.lists` → `[{ name: "Work", total: 2, undone: 1 }, { name: "Home", total: 1, undone: 1 }]`;
  `app.lists["Work"]` → that one list.
- `app.tags` → name, colour and carrying-item count per tag.

### M.3 — writable properties

`app.selectedList = "Home"` round-tripped, and the root summary's `shown` fell from 3 to 1.
`app.selectedList = "Nope"` returned `{ ok: true }` — a remote assignment is fire-and-forget — and
the read-back still said `"Home"`: the setter refused an unknown list and left the selection alone,
which is exactly the "visible on a later read" contract the library documents. The member summary
says *"Must be an existing list"*, so an agent is told before it tries.

### M.4 — methods

Every method was called. Representative results:

| Call | Result |
|---|---|
| `addItem("Buy milk", "Groceries")` before the list existed | `Error: No list named "Groceries". Create it with addList("Groceries") first.` |
| `addList("Groceries")` | `"Groceries"` |
| `addItem("Buy milk", "Groceries")` | the new item's uuid |
| `setItemTag(id, "errand")` | `"errand"` — the tag did not exist and was created, as its summary promises |
| `toggleItem(id)` | `true` |
| `setItemTitle` / `setItemComment` | the new value, written immediately (not on the UI's 300 ms debounce) |
| `setTagColor("errand", "chartreuse")` | `Error: Invalid color "chartreuse". Use setTagColor with "" or one of: dodgerblue, hotpink, …` |
| `setTagColor("errand", "limegreen")` | `"limegreen"` |
| `renameList("Home", "House")` / `renameTag("urgent", "hot")` | the new names; items moved with them |
| `deleteItem` / `deleteTag` / `deleteList` | `true`, immediately — **no** in-board confirm overlay, which is the whole reason for the `*Core` split |

`pages[id].content` then showed every change in the host's copy of the file, correctly serialized
with 4-space indent, and the page was marked modified. The file on disk was untouched until a save,
which is the content-host contract.

### M.5 — elements and highlight

`app.elements` listed all seven declared controls with resolved selectors and `visible: true` —
including the four that live in the `lists` secondary frame, because the host routes `ai:elements`
per declaration `view` and auto-mounts the panel. `highlight("quick-add-input", …)` and
`highlight("tags", …)` both returned `found: true, count: 1`, the second one drawing inside
`board-secondary:lists`.

### M.6 — `helpSearch`, and the wording defect it exposed

`helpSearch("add a todo item")` initially returned the `quick-add-input` element and the board's
`$help` — but **not** `addItem`. `matches()` in the library requires *every* query token as a
substring, so a summary reading "Add an item and return its id" cannot match a query containing the
word "todo". That is a property of the search, not a bug in it (built-in surfaces share it), but it
puts a real obligation on descriptor prose: **write member summaries in the words a user would use,
not the words the API uses.**

Six method summaries were rewritten accordingly — "Add a new **todo item** to a list…", "**Mark** a
todo item **done, or undo it**…", "**Rename** a todo item…", "Add or replace the **comment (the
note)**…", "**Put a tag on** a todo item, or null to **take it off**…", "**Remove** a todo item from
the list…". `helpSearch("add a todo item")` then returned `page.editor.app.addItem()` as its first
hit.

### M.7 — reload and the empty-file case, and the two host defects

`pages[id].editor.reload()` re-registered the shape and `.app` resolved again immediately.

Opening a **brand-new, empty** `.todo.json` and calling `app.addList("Groceries")` failed with
`Error: Board AiVision registration was replaced.` — while nevertheless creating the list. Two host
defects behind it, both fixed in this epic:

1. **A `refresh()` was treated as a new remote.** `expose()` derives the shape of an indexed item by
   probing `index(0)` once, at registration time, so a board that registers before its async load —
   as this one must — publishes empty collections with no item shape, and calls
   `remote.refresh()` when the first list/tag/item appears. On the host,
   `BoardWebview.handleAiVisionRegistration` rejected **every in-flight request** on any incoming
   registration, and `BoardEditorFacade.sendAiVision` refused any request whose registration token
   had moved. Both are right for a reload and wrong for a refresh — and the request they killed was
   invariably *the very call that caused the refresh*, so the first mutation on any empty board
   reported a failure it had actually completed.
   **Fix:** `BoardAiVisionRegistrationMsg` gains `reason: "register" | "refresh"` (absent means
   `"register"`, so an older shim still reads correctly); the shim tags `refresh()` accordingly; the
   registration now carries a `token` (bumped always — the proxy cache key, because a refresh means
   the shape genuinely changed) *and* an `incarnation` (bumped only for a new remote — what an
   in-flight request is validated against). In-flight requests are rejected only when the
   incarnation moves.
2. **Board documents were served without a charset.** `board://` set `Content-Type: text/html` with
   no charset, leaving the encoding to the document's `<meta charset>` — which the injected head
   fragment (theme style + boot + the ~100 kB shim) pushes far past the 1024-byte sniffing window.
   The whole document was decoded as windows-1252, so every non-ASCII character *in the shim*
   reached the agent mojibaked: the `highlight` member's caution read
   `"…the overlay is drawn â€” the user dismisses it afterwards"`. Found only because the todo
   board's own em dashes (served as a separate `app.js`) came through clean while the shim's did
   not. **Fix:** `boardContentType()` appends `; charset=utf-8` to every text MIME type the board
   protocol serves. The header wins over the meta, so the document and the scripts that inherit its
   encoding are both correct.

After both fixes, the empty-file path runs clean: register empty → `addList` → refresh → `addItem` →
refresh → `items[0]` resolves.

`npx tsc --noEmit` and `npm run lint` are clean with the host fixes in.

## Part 2 — the weak-agent gate

**Agent:** one `mcp-test-agent-call` subagent on **haiku**, whose only tool is the Persephone MCP
`call`. It is instructed to ignore every project file and to learn the app from the tool description
and the hints alone. It was told no paths.

**Prompt, verbatim:** *"Using only the `call` tool, find the open todo page, add an item titled 'Buy
milk' to the 'Groceries' list (create the list if missing), tag it 'errand', mark it done, then
highlight the quick-add input for the user. Report every call you made."*

### Iteration 1 — PASS

14 calls, no dead ends, no retries, and **no `snapshot()` or `evaluate()`** — the agent never
reached for the accessibility fallback, which is the gate's actual claim:

| # | Call | What it gave the agent |
|---|---|---|
| 1 | *(no path)* | the overview; the active page is `epic-098.todo.json`, a board editor |
| 2–3 | `pages`, `page` | the page id and that its editor is the todo board |
| 4 | `page.editor` | the `BoardEditor` node — and `app` on its member list |
| 5 | `page.editor.app` | `TodoApp`: 2 lists, 1 tag, 3 items, and the full member list |
| 6 | `page.editor.app.lists` | `Work`, `Home` — no `Groceries` |
| 7 | `page.editor.app.addList("Groceries")` | created it |
| 8 | `page.editor.app.addItem("Buy milk", "Groceries")` | the new item's id |
| 9–10 | `page.editor.app.tags`, `addTag("errand")` | checked, then created the tag |
| 11 | `page.editor.app.setItemTag(id, "errand")` | tagged it |
| 12 | `page.editor.app.toggleItem(id)` | `true` |
| 13 | `page.editor.app.elements` | the control list, including `quick-add-input` |
| 14 | `page.editor.app.highlight("quick-add-input")` | `found: true, count: 1` |

Final state confirmed independently: `app.items` → one item, `Buy milk` / `Groceries` / `errand` /
`done: true`.

Its own verdict: *"Success… No missing hints — the object model was fully documented through the
hints system, and every required operation had a corresponding method."*

**No further iterations were needed.** The budget was three; one was spent.

Two things in the transcript are worth keeping, because they are what the descriptor prose bought:

- The agent checked `lists` **before** calling `addList`, and `tags` before `addTag`. Nothing told
  it to; the collection summaries ("Every list in the file, with total and undone item counts")
  made looking cheaper than guessing.
- It never had to be told that `setItemTag` and `toggleItem` take an **id** rather than a title. It
  carried the id returned by `addItem` straight through — the `addItem` summary says it returns the
  id and every `…Item` signature says `id: string`.

The one thing the agent got for free that a stricter run would not: `addTag("errand")` before
`setItemTag`, which the board would have done for it anyway (an unknown tag is created). Belt and
braces, not a stumble.

## What this run says about the roadmap

The roadmap's closing claim was that a board could be made as drivable as a built-in editor by
publishing a data contract, with the engine staying on the host. A haiku-class agent with one tool
and no guide did the whole job in 14 calls on its first attempt. The mechanism is ready for the
other built-in editors planned to move to boards, and the todo board's `app.js` is the worked
example they should copy — including its two non-obvious parts: the `*Core` split that keeps an
agent's delete off the confirm dialog, and the `refresh()` rule for indexed collections that start
empty.

The three defects the run found are the argument for running a gate like this at all: two of them
were in the *host*, shipped and green two hours earlier under a synthetic scratch board, and only a
real board with an async load and a genuinely empty starting state produced them.
