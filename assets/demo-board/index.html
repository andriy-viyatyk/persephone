Persephone Boards

A living demo & reference — what a board is, how to theme it, what it can do, and how to build one.

What is a Board?

A Board is a small local application whose UI you own as a plain HTML page, backed by scripts you write in any language. Persephone hosts the page in a locked-down, cross-origin <iframe> and injects a single bridge object, window.persephone. Persephone owns no board state and no board UI — it just wires the bridge and shows the page. A board lives in its own folder anywhere on disk — recognized by a board-manifest.json at its root. A board can be created or opened from any path; the Create-board dialog defaults to the current file-explorer root.

How it works — frontend + backend + a channel

  • Frontend — index.html + app.js (+ any CSS/assets). Owns all UI and all state. This is what renders in the iframe.
  • Backend — scripts under scripts/ (.js, .py, .ps1, .sh, …). They run as real OS processes with your privileges and talk to the page over stdout.
  • Channel — persephone.execute(commandLine). The page calls a script, the script prints to stdout, the page reads it and renders. That's the whole loop.

Built by an agent, not by hand

Boards are meant to be authored by an AI coding agent — Claude Code, for example — rather than hand-written. There's deliberately no in-board editor, debugger, or dev console: the host stays minimal on purpose. And a board is made of exactly what an agent is best at — raw HTML, vanilla JavaScript, and Node or Python scripts — so the fastest way to build one is simply to ask.

Describe the report, tool, or mini-application you need, and your agent scaffolds the page, wires persephone.execute() to a backend script, and themes it with the --p-* variables — usually in a few minutes. You review the result and refine it in plain language.

    Theme with the --p-* contract

    Persephone injects its palette as CSS variables on <html> and keeps them live across theme switches. Style everything with them and your board matches the app automatically — switch the app theme (dark ↔ light) and watch this whole page restyle live, with no JS.

    body { background: var(--p-bg); color: var(--p-text); }
    button { background: var(--p-accent); border-radius: var(--p-radius-md); }

    Colors update with the theme; metrics (--p-space-*, --p-radius-*, --p-font-*) are constants. Also mirrored in JS as persephone.theme / persephone.tokens / persephone.onThemeChange(cb) — for colors you set from JS.

    Persephone chrome — the .p-* classes

    board-base.css ships the app's toolbar and controls as ready-made classes. They are opt-in — a bare <button> is untouched, so a vendored library's own controls keep their styling. Use them instead of hand-styling chrome: the sizes below are the app's, which is what makes a board look built in rather than embedded.

    Board title

    That bar is 30px tall (31px once the bottom rule is counted) on --p-bg-dark, and the buttons in it are 24px — the app's small button, which is what Persephone's own editor toolbars are built from. Putting .p-btn in a .p-toolbar shrinks it for you; add .md if you really want the 26px page size in a bar. The three mistakes this exists to prevent: a comfortable-looking padding: 8px 12px makes the bar 45px, half again too tall; painting it on --p-panel makes it pale, because app chrome is darker than the page, never lighter; and filling it with 26px buttons looks fine on its own but oversized the moment it sits under the app's chrome.

    The set

    .p-toolbar 30px bar (data-orientation="vertical" for a rail) · .p-btn 26px button, 24px in a toolbar — primary, ghost, danger, link, selected, icon, sm, md, on-dark · .p-input / .p-select field, same two sizes · .p-sep · .p-spacer · .p-toolbar-title

    Writing your own chrome instead? Keep the numbers: fixed height with horizontal padding only — vertical padding on a button is the usual cause of an oversized bar. In a bar: height: 24px; padding: 0 4px, 12px text. Outside one: 26px, 0 8px, 14px. Everywhere: 4px radius (the same radius on every button in a bar), 4px between controls, 6px inside one, 16px icons.

    persephone.execute() — run scripts & tools

    The one method. Buffer the result (getText/getJson/getBytes) or stream it (on("stdout"/"exit"/…), write, kill). These probes spawn node, so Node must be on PATH — for a runtime that always works, see executeNode() below.

    persephone.executeNode() — bundled Node runtime

    Runs a script on Persephone's own Node — no Node install needed on the machine. Same handle as execute(); args pass argv-style (no shell). The runtime is Node 24 with node:sqlite built in. Spawn once and feed a resident server JSON lines over stdin instead of a spawn per operation.

    Integration tier — in-app effects

    Effects execute() can't express: toasts, opening links/pages, native dialogs.

    persephone.call() — inspect the hosting page

    A trusted Board can resolve the page-scoped AiVision tree through its hosting page. Results are JSON-safe; append .$describe to a node path for its structured descriptor, while $help remains the prose form. The hosting page stays fixed if another tab becomes active; process-wide main.* and windows[i].* paths belong to the MCP call tool instead.

    Secondary views & shared state

    A board can contribute secondary views — extra sidebar panels, each its own board:// iframe over the same board. Every frame (main + each secondary) shares one Persephone-owned state object via persephone.state.*, so they stay synchronized. This is the plumbing for editor-style boards — a main view plus a coordinated sidebar. This demo declares two secondary views:

    Anatomy of a board

    • board-manifest.json — the board-identity file (schemaVersion: 1 + optional metadata: name, description, author, repository). Its presence is what marks the folder as a board. Custom-editor behavior fields are optional and trust-gated; see the authoring guide for fileMasks, folderMasks, and direct-folder folderEditorMasks.
    • index.html — your page. Edit it, then hit Reload in the board toolbar to apply.
    • app.js / style.css — your logic and styling (reference relatively, e.g. ./app.js). Boards don't auto-reload — use the Reload button in the board toolbar (or call at pages[i].editor.reload() when an agent is driving) to apply edits.
    • scripts/ — backend scripts in any language, invoked via persephone.execute("scripts/thing.js"). cwd defaults to the board folder, so relative paths just work. For a Node script that must run on any machine, use persephone.executeNode("scripts/thing.mjs") — it runs on Persephone's bundled Node (no install needed).

    Returning data reliably

    A bare getJson() assumes stdout contains only your JSON. The moment a script shells out to a tool that prints its own output, that breaks. Two habits fix it:

    • Logs → stderr, result → stdout. Send diagnostics to stderr; capture sub-tool output instead of letting it flow through.
    • Wrap the result in a marker and extract it: emit "@@RESULT@@" + JSON.stringify(x) from the script, then read it with execute(cmd).getJson(/@@RESULT@@(.*)/). It extracts the match before parsing and still rejects on a non-zero exit with the captured stderr.

For the common cases we recommend a short list of well-behaved components and publish a Persephone skin for each — a --p-*-themed CSS skin, or a small JS adapter for canvas / JS-colored libraries that have no stylesheet to override — so a dropped-in component matches the app theme out of the box.

    Debugging a board with an AI agent

    A board has no built-in editor or dev console — you debug it the same way you build it: through an AI agent connected to Persephone's MCP server. The agent reads the live page, clicks and types, and runs JavaScript inside the board through the call path on the board's page editor.

    1 · Enable the MCP server in Persephone

    Open Settings → MCP Server and:

    • Check Enable MCP server (off by default).
    • Leave the Port at 7865 (changing it requires toggling the server off and on).

    The server listens on http://127.0.0.1:7865/mcp. A Copy Config button there gives you the ready-to-paste snippet below.

    2 · Point your agent at it

    The transport is HTTP (not stdio). For Claude Code, add to .mcp.json (project root or ~/.claude/.mcp.json):

    {
  "mcpServers": {
    "persephone": {
      "type": "http",
      "url": "http://127.0.0.1:7865/mcp"
    }
  }
}

    Claude Desktop: add an MCP server named persephone with the same URL. Reconnect the agent after changing its MCP client configuration so it picks up the current tools.

    3 · Open the board, then drive it

    An agent can create and open a board itself — call paths boards.createBoard / boards.createDemoBoard scaffold one (auto-trusted) and boards.openBoard opens it, no clicks needed. A board the agent did not create (a foreign folder you received) prompts you for trust before it renders — so for those, you open/trust first. Either way, the agent then:

    • call at pages → find this board (editor: "board-view", with its selectedBoard) and read its pageId.
    • call at pages[pageId].editor.snapshot() → read the accessibility tree (element refs).
    • call at pages[pageId].editor.click/type/pressKey(...) → interact, using refs from the snapshot.
    • call at pages[pageId].editor.evaluate(...) → run JS in the page: inspect state, read --p-* values, poke the DOM. The most useful probe when something looks wrong.
    Always include the board's pageId in the pages[pageId].editor path — otherwise you may inspect the wrong page. Navigation and tab tools don't apply: a board is one fixed page.

    Tips

    • Boards don't auto-reload — after editing index.html, app.js, or any .js/.css, hit Reload in the board toolbar (agents use call at pages[pageId].editor.reload()) to apply changes.
    • Failures reported via persephone.notify(msg, "error") are toasted and appended to the board's ui.log (open it with Show-log in the toolbar) — check there first when a board misbehaves. Load failures, CSP violations, uncaught errors, and every console.error/console.warn from the board's frames land there automatically; the log starts fresh on each load.
