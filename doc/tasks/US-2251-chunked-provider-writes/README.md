# US-2251: Chunked provider writes

[EPIC-218](../../epics/EPIC-218.md) · Planned

## Goal

Allow content providers to accept a stream of chunks without the buffered pipe limit, with commit or cleanup on abort.

## Background

EPIC-218 and Phase 2 of the [remote trees roadmap](../../reviews/remote-trees-roadmap.md) require optional chunked writes on the existing provider channel, a local-file implementation, and buffered fallback for providers without the capability. US-2252 owns the transfer engine; US-2256 owns UI tests.

`IProvider` is declared in `src/renderer/api/types/io.provider.d.ts`: it has optional `writeBinary` and `createReadStream`, but no streaming write. `FileProvider` uses Node filesystem I/O directly; `ProxyProvider` calls `moduleService.request` and caps `writeBinary` at `MAX_BUFFERED_PIPE_BYTES` (256 MiB). `src/shared/board-pipe-constants.ts` also defines a 1 MiB board-pipe chunk limit. `src/module-service-host/service-api.ts` installs service `persephone.providers.register`; its implementation and capability announcement are owned by `src/module-service-host/provider-dispatch.ts`.

The bridge history is actually `assets/guides/agents/boards/bridge-versions.md`: 1.64.0 explicitly includes the host-service `treeProviders.register` API; 1.65.0 adds `openTree` and extends `openRawLink`. Follow that precedent: service registration methods are bridge surface, so bump `src/shared/board-bridge-version.ts` from 1.65.0 to 1.66.0 and add a history line.

The provider traffic goes directly between renderer and utility-process ports after main establishes a lease (`src/main/module-service/leases.ts`); `src/renderer/api/module-service.ts` owns per-request deadlines and cancellation, and `src/module-service-host/renderer-lease.ts` aborts pending controllers on cancel or lease loss. It does not currently track completed begin operations. `provider-dispatch.ts` validates `readRange` against the 1 MiB constant and buffered writes against 256 MiB. `MAX_SERVICE_CHANNEL_MESSAGE_BYTES` is also 1 MiB, but applies to the separate service-channel abstraction, not this provider port; use the existing 1 MiB range bound for provider chunks rather than claiming that abstraction enforces it here. The default capability deadline is 10 seconds and the outstanding control-request cap is 32 per lease.

`IContentPipe` exposes its provider and transformer list; `ContentPipe.writeBinary` applies transformers in reverse. Direct provider writes would bypass those transformations. `MissingProvider` in `src/renderer/content/registry.ts` delegates `createReadStream` dynamically and must likewise delegate the optional write capability.

The US-2248 board is `integration-test/fixtures/boards/trees/tree-board/scripts/service.mjs`, with manifest alongside it; the completed epic identifies `boards/trees` fixtures. It has separate `a`, `b`, and `ro` maps, buffered reads and writes, and no `readRange`. Its current `writeBinary` requires an existing file.

## Implementation Plan

- [x] **Contract and limits — `src/renderer/api/types/io.provider.d.ts`, `assets/editor-types/io.provider.d.ts`, `src/shared/board-pipe-constants.ts`.** Add an optional `beginWrite(options?: { signal?: AbortSignal }): Promise<IProviderWrite>` to `IProvider`, with `IProviderWrite.write(chunk: Buffer): Promise<void>`, `commit(): Promise<void>`, and idempotent `abort(): Promise<void>`. Absence means buffered fallback; do not pretend every provider streams. Each session accepts sequential awaited writes, max 1 MiB each, including zero chunks for an empty file. Reject concurrent operations on a session, oversize chunks, and writes/commit after termination. `abort` after termination is harmless. The signal remains associated with the session through commit/abort, including the begin race. Document that successful commit replaces the target; errors propagate. Reuse `MAX_BOARD_PIPE_CHUNK_BYTES` for both read ranges and chunks; add a service-wide open-write cap of **16**, counting starting and closing sessions across all leases and provider types, in the same constants module. Reject the 17th with a clear busy error; release only after cleanup settles, not merely on cancellation. No total transfer deadline.

  ```ts
  // Before: optional buffered write only
  writeBinary?(data: Buffer): Promise<void>;
  // After: buffered write remains; optional transactional session
  writeBinary?(data: Buffer): Promise<void>;
  beginWrite?(options?: { signal?: AbortSignal }): Promise<IProviderWrite>;
  ```

- [x] **Policy and wire — `src/shared/provider-operation-policy.ts`, `src/ipc/module-service-channels.ts`.** Add `writeBegin`, `writeChunk`, `writeCommit`, `writeAbort` as control operations with 10,000 ms each, reusing `CAPABILITY_DEFAULT_TIMEOUT_MS`; the deadline is per request, never per file. Extend `ProviderRequest`, success variants of `ProviderResult`, and `ProviderCapabilities` with a bounded opaque write ID and `chunkWritable` boolean. Generate the ID in the renderer before begin so cancellation can identify a begin still in flight; bind it to the renderer lease, provider type, and config at begin, reject duplicate/unknown/cross-lease IDs, and use stored config thereafter. Reuse the existing request IDs, `provider-result`/`provider-error` and cancel messages; the write ID identifies a resource, not a new request correlator. Explicitly validate `Uint8Array` and size at the host, copying with existing `copyBytes`.

- [x] **Board service contract and state — `src/module-service-host/provider-dispatch.ts` and a new `src/module-service-host/provider-write-sessions.ts`.** `ProviderImplementation` gains the all-or-none optional methods `writeBegin(config, { signal })`, `writeChunk(handle, data, { signal })`, `writeCommit(handle, { signal })`, `writeAbort(handle)`; begin returns a board-private handle, never serialized. Require `writable: true` and the entire set; retain the current `writeBinary` requirement for existing writable behavior. Reject partial registrations. Advertise `chunkWritable` only for the complete set, as `rangeReadable` does. Keep validation and dispatch at the existing boundary; put the state machine, global limit, serialized cleanup, ID ownership, and race handling in the new collaborator, reusing the dispatch's existing validation/copy and provider error functions. The board implementation owns target-specific temp creation, data writes, rename/replacement and deletion: create a unique temp in the target namespace, commit by rename, and abort by deleting only that temp. It must support a new destination and preserve an existing destination until commit. No board path or trust rules move out of `src/shared/board/` or registries.

  ```ts
  // Before
  persephone.providers.register(type, { readBinary, writable: true, writeBinary });
  // After (all four chunk methods are optional as a group)
  persephone.providers.register(type, { readBinary, writable: true, writeBinary,
      writeBegin, writeChunk, writeCommit, writeAbort });
  ```

- [x] **Cancellation and lease lifecycle — `src/module-service-host/renderer-lease.ts`, `src/module-service-host/index.ts`, session collaborator, `src/renderer/content/providers/ProxyProvider.ts`.** Reuse each request's existing `AbortController` and `cancel` delivery; route cancellation of begin/chunk/commit to the session owner as well as aborting the controller. A renderer signal abort, timeout, write failure, provider disposal, or lease loss marks the session aborting exactly once and invokes board `writeAbort` after any in-flight operation settles; late begin completion must immediately abort its returned handle, even if the original request already timed out. Prevent further chunks or commit while aborting. Extend lease close with an injected session-cleanup callback; avoid storing business state in the lease manager. The proxy retains an abort listener throughout the session and sends a separate `writeAbort` without the already-aborted signal, even when begin's reply is lost; host cleanup is authoritative if that message cannot be sent. Serialize commit against abort: after commit has actually succeeded the destination is committed, and cancellation cannot undo it; before then the board must cooperate with the signal and must not publish after abort. Never report an uncertain timed-out commit as success.

- [x] **Service death and recovery — `assets/guides/boards/content-providers.md`.** A killed utility process cannot invoke `writeAbort`, and main has neither the remote credentials nor the temp names. Recommend that boards with persistent targets use a durable, connection-scoped temp journal or identifiable exclusive temp namespace and reconcile their own uncommitted orphaned entries on the next service start or connection, before accepting new writes. The host does not enforce this recommendation. In-memory boards lose the uncommitted map automatically on process death. A crash during rename has an inherently uncertain commit outcome; recovery should distinguish a completed rename from an orphan and never delete the destination. Cleanup is eventual when the board implements recovery and reconnects; it cannot be guaranteed immediately or if the board or remote host never reconnects. Document cancellation cooperation, cleanup failure reporting, idempotence, and the recovery recommendation in the board guide. Add no host-side crash-recovery code or remote cleanup protocol.

- [x] **Renderer — `src/renderer/api/module-service.ts`, `src/renderer/content/providers/ProxyProvider.ts`, `src/renderer/content/registry.ts`.** Cache and clear `chunkWritable` alongside `rangeReadable` per lease, expose a getter only when announced, with no config fallback; delegate through `MissingProvider` exactly as its `createReadStream` getter does. Put proxy session behavior in `src/renderer/content/providers/proxy-write-session.ts`, reusing `moduleService.request`, existing `providerResultError` / `invalidProviderResult`, and the policy table. Verify response operation, IDs and limits. Retain `writeBinary` and its clear 256 MiB failure. US-2252 consumes `pipe.provider.beginWrite` only when `pipe.transformers.length === 0`; transformed targets must use `pipe.writeBinary` and remain bounded, never silently bypass transformers. US-2252 owns buffering and the explicit oversized-fallback error; state this dependency in its plan.

- [x] **Local filesystem — `src/renderer/content/providers/FileProvider.ts` and a focused `src/renderer/content/providers/file-write-session.ts`.** Implement the same session contract using the existing low-level `nodefs` exception: create an exclusive unique sibling temp, write sequentially using a file handle (handle partial writes), close then rename to target on commit, close/unlink on abort or failure. Reuse `fpDirname` / `fpJoin` from `src/renderer/core/utils/file-path.ts` rather than a direct path import. Ensure replacing an existing target follows platform rename semantics without deleting it first; propagate unsupported replacement errors. When the target is open in an editor, rely on the existing file watcher to trigger reload; no editor-side change is planned in this task. Handle begin/abort races, signal listener removal, empty files, cleanup failures, and dispose-owned sessions. Process termination may leave a local temp; use an identifiable exclusive naming scheme and document that recovery requirement rather than deleting unrelated files.

Update `writeBinary` to create a new file when its parent folder exists, so US-2252's buffered fallback can create destinations; still refuse writes on `ro`. Existing `a` and `b` already provide separate trees. Set its `minBridgeVersion` to 1.66.0.

## Concerns / Open questions

- **Hard-crash cleanup is eventual, not immediate.** A dead board service cannot receive abort; recovery is recommended for boards with persistent targets and belongs to the board implementation on its next connection. The host does not enforce recovery, and a board without recovery or a permanently unreachable remote can leave an orphan. Cancellation racing an already-completed rename may leave the committed target; report this honestly. The documented guarantee is no partially published target, subject to the board and destination's rename semantics.
- **Local process crash:** a sibling temp can survive renderer/application death. Do not sweep arbitrary sibling files; a safe persistent ownership journal and recovery design would be required for guaranteed crash cleanup. Ordinary cancellation and provider disposal must clean up.
- **Fallback and transformers:** the transfer engine is US-2252; it must enforce bounded buffered fallback and avoid direct provider writes on transformed pipes. Chunked writes alone do not make transformed content streamable.

## Acceptance Criteria

- Writable providers can opt into ordered bounded writes; unsupported providers retain existing buffered behavior and the transfer engine has a specified safe fallback.
- Local and board sessions publish complete bytes only on successful commit; abort and ordinary cancellation remove staged data and preserve an existing target. Empty and multi-chunk files work.
- Requests use the existing channel and errors, 1 MiB chunks, 10-second per-operation deadlines and a 16-open-write service-wide limit. Cancellation, late begin completion and lease loss trigger cleanup; service crash recovery and commit ambiguity are documented accurately.
- Capability detection survives absent providers and service reattachment; partial board registrations are rejected; read-only connections remain protected.
- Bridge version and history are updated; the tree fixture supports the new API. Required typecheck, lint and guide checks pass; US-2256 owns the listed UI coverage.
