# US-2151: Page-model replies: navigation, truncation, key order

[EPIC-203](../../epics/EPIC-203.md) · G1, G3, G4 · feedback [1, 4, 8](../US-2138-web-app-test-feedback/README.md)

## Goal

Make a page-model invocation interrupted by navigation recognizable, stop returning silently cut model replies, and preserve the page's object-key order where Persephone controls it.

## Background

- `BrowserEditorFacade.getAiVisionProxy` in `src/renderer/scripting/api-wrapper/BrowserEditorFacade.ts` mounts the active document's shape through ai-vision `createRemoteProxy`. A method is invoked with an `args` array; the proxy passes **all** entries as positional model arguments in `IAiRemoteRequest { action: "ai:invoke", path, args }`. A trailing options object would collide with legitimate model arguments. `BrowserPageRemote.request` in `src/renderer/editors/browser/BrowserPageRemote.ts` calls `remote.handle()` in the registered document using `evaluateInTarget`, with readiness and timeout checks. The proxy separately revalidates the shape before dispatch. A navigation before dispatch can therefore yield the existing stale-document refusal; G1 covers context loss during the actual invocation, not every stale binding or every error mentioning navigation.
- `evaluateInTarget` in `src/renderer/automation/queries.ts` runs the expression with CDP `Runtime.evaluate` and, for its object result, obtains a by-value copy with `Runtime.callFunctionOn`. CDP can fail with `Cannot find context with specified id`. `request` currently catches non-timeout errors and returns `{ ok: false, error: errMessage(...) }`, losing their code. ai-vision's proxy rethrows a response's `code`; `resolveCall` retains it and `src/main/mcp/tools/call-tools.ts` formats `Error [code]: ...` (EPIC-199). `src/test-host/client.ts` extracts that code onto the thrown `Error`.
- The installed `ai-vision` 1.4.0 `dist/remote/expose.js` calls `shapeResult(value, request.maxLength)` in the page. `createRemoteProxy` does not put `maxLength` in its request and its `sendRequest` returns only `response.result`, discarding `truncated`, `shown`, `total` and `totalLength`. Thus the inner default 20,000-character cut loses its marker before the outer resolver shapes the value. Claude verified this live with a 365-row, four-key reply: 220 items arrived without an inner marker; with `maxLength: 300`, outer shaping then reported "showing 3 of 220 items". The original feedback reported 153 items. `src/test-host/client.ts` can reject an outer `[truncated:` block, but cannot detect this lost inner marker. `MAX_AI_VISION_SHAPE_BYTES` in `BrowserPageRemote` limits registration shapes, not replies. The site-extension runtime `src/site-extension-runtime.ts` uses `ai-vision/remote` `expose`; independently authored page runtimes may use another version. The separate WebMCP remote in `src/preload-webview/webmcp-bridge.ts` parses tool output and returns it directly, without `shapeResult` or `maxLength`; it sorts tool names for the descriptor, not result keys. Its `executeTool` null result is a separate uncoded navigation error.
- `shapeResult` also imposes a 500-item array limit and depth 8; these use in-value markers and are independent of `maxLength`. For an array longer than 500, `node_modules/ai-vision/dist/core/result-shaper.js` returns the first 500 elements followed by `{ kind: "truncated", note: "N more items" }`, where N is the omitted count; no structural-limit code change is planned here. Nested long strings receive an in-value length marker. These are not the lost top-level length metadata and raising `maxLength` does not remove the structural limits. Do not claim all data is unlimited. Images have a special top-level exemption. `src/renderer/scripting/ai-vision/call-limits.ts` only removes the **outer** default for scripts and boards today; it does not propagate that limit to the page remote.
- Installed ai-vision `dist/core/result-shaper.js` copies plain objects with `Object.entries`, without sorting, and MCP's `toCallResult` uses ordinary `JSON.stringify`. Claude's live comparison established that CDP's by-value transfer through Chromium's protocol dictionary sorts keys: `editor.app.ordered()` returned sorted keys at every level, and `editor.evaluate` returned sorted object keys while an in-page `JSON.stringify(Object.keys(...))` string retained insertion order; a renderer `script.execute` result also retained insertion order. `Runtime.callFunctionOn` with `returnByValue: true` in `src/renderer/automation/queries.ts` is the relevant boundary. JavaScript integer-index keys enumerate numerically even when inserted differently. Integration tests in `integration-test/tests/capabilities/module-service/module-service.test.mjs` and `integration-test/tests/boards/bridge/bridge.test.mjs` sort selected values themselves; no general dependency on alphabetized page-model replies was identified.
- Board frame `src/renderer/editors/board/frame/ai-vision-bridge.ts` and `src/renderer/editors/board/model/BoardAiVisionChannel.ts` route a **board's exposed model** through the same remote-proxy pattern, but do not handle browser page requests. Conversely `src/renderer/api/boards/board-host-rpc.ts` resolves a board's `persephone.call()` against the app tree: it can reach a browser page's `.editor.app`, so browser reply order, length, and failures are observable by boards. It currently throws `new Error(result.error)` and wraps errors, losing `result.code`. `AppWrapper.call` preserves codes with `codedError`. This task changes board-observable results even without a new board API; extend the epic's shared bridge history entry.

## Implementation Plan

- [x] **Call options and ownership.** Put `allowNavigation?: boolean` alongside `path`, `args`, `maxLength`, and `timeoutMs` in the MCP `call` schema (`src/main/mcp/tools/call-tools.ts`), `McpCallParams` (`src/ipc/renderer-rpc.ts`), validation and request assembly (`src/renderer/api/mcp/call-command.ts`), and per-call `IAiCallContext` (`src/renderer/scripting/ai-vision/root.ts`, populated in `call.ts`'s `resolveAiCall`). This follows the existing `timeoutMs` call-option precedent, which applies under `pages[i].editor.app`; describe `allowNavigation` in the schema as "applies only to a page-model method call under pages[i].editor.app". Reject non-booleans as `invalid-params`; omitted is false. Scope it to browser page-model **method invocations**; ignore it for other paths and actions. Do not add it to `IAiRemoteRequest.args`. Extend runner `CallOptions`, `context.ts`, and `client.ts` so `ctx.call(path, args, { allowNavigation: true })` and `ctx.app.withOptions({ allowNavigation: true }).pages[id].editor.app.method(...)` forward it as a call option. Ensure `callText` and `waitFor` pass the same option where their existing `CallOptions` applies. Keep transport and client timeout distinct from `timeoutMs`.

  ```js
  // Before: the last object is a page method argument.
  ctx.call('pages["id"].editor.app.submit', [{ allowNavigation: true }]);
  // After: unchanged model arguments, separate host call option.
  ctx.call('pages["id"].editor.app.submit', [], { allowNavigation: true });
  // MCP call tool: { path: 'pages["id"].editor.app.submit', args: [], allowNavigation: true }
  ```

- [x] **Navigation rule.** `BrowserPageRemote` owns the rule; a focused collaborator `src/renderer/editors/browser/page-model-reply.ts` can classify and shape the response while `request` retains document/timeout ownership. Pass the per-call option from the facade's existing call context into `request`, separately from the remote request. Isolate the evaluate failure from `ensureTargetReady` so preflight errors remain unchanged. Only when `request.action === "ai:invoke"` and the evaluate operation fails with the specific context-loss message, return `{ ok: false, code: "page-navigated", error: "Page navigated during the model call; its result is unavailable." }`, or `{ ok: true, result: { navigated: true } }` when opted in. Reuse `errMessage` for inspecting the caught value and the existing `IAiRemoteResponse` / ai-vision coded-error path; do not classify arbitrary application errors, timeouts, preflight refusals, tab changes, or successful replies as navigation. No retry: the action may already have happened. No new correlator, acknowledgement, or error envelope.

  ```ts
  // Before
  return { ok: false, error: errMessage(error, "The browser page AiVision call failed.") };
  // After (specific invocation context loss; other errors retain the existing branch)
  return allowNavigation
      ? { ok: true, result: { navigated: true } }
      : { ok: false, code: "page-navigated", error: "Page navigated during the model call; its result is unavailable." };
  ```

- [x] **Reply size.** Carry the effective call `maxLength` in the existing renderer call context (MCP uses its existing 20,000 default; `AppWrapper.call` and `board-host-rpc` pass their existing `UNBOUNDED_CALL_MAX_LENGTH` default or explicit option). `BrowserPageRemote.request` passes it as the existing `IAiRemoteRequest.maxLength` to the selected page/WebMCP remote. In the reply collaborator, inspect successful `response.truncated` **before** `createRemoteProxy` discards it and replace that response with existing `{ ok: false, code, error }`: use `result-truncated`, naming the effective character cap, `shown`/`total` or `totalLength` where supplied, and `maxLength` as the option to raise. Do not mistake model data containing `truncated` for response metadata. Preserve other errors and normal results. For WebMCP, which does not shape its reply, the collaborator must apply the existing ai-vision `shapeResult` to its successful result at the same effective cap and turn its truncation metadata into the same coded error before proxy unwrapping; preserve the top-level image exemption. This covers a page remote that honors the existing request and reports its cut; do not fabricate completeness for an arbitrary page-authored remote that silently omits metadata. The outer MCP cap still has its existing marker for non-model calls. Explicitly bounded page-model calls fail rather than deliver a partial value. Preserve the existing structural markers and describe their independent limits.

  ```ts

  return response;
  // After: at the browser page boundary, before the proxy unwraps it.
  if (response.ok && response.truncated) return { ok: false, code: "result-truncated", error: `Page model reply exceeded maxLength (${maxLength}); raise maxLength.` };
  return response;
  ```

## Concerns

- The option is deliberately a host-call option, not a positional model argument. It reports a lost reply, not proof that navigation finished or that the action succeeded. Pre-dispatch stale-model and same-document reprobe behavior are outside this task.
- Page-authored remotes can implement `handle` differently or use older ai-vision. Only metadata actually returned can prove a cut; the required live check uses the bundled temporary extension runtime. Do not promise detection of arbitrary silent truncation performed by page code. The fixed array/depth markers are not raised by `maxLength`; arrays of pairs remain appropriate for application-level ordering where needed.
- `editor.evaluate` keeps Chromium's sorted object keys; the browser guide should say to return `JSON.stringify(...)` from `evaluate` when key order matters. General evaluate serialization is a candidate for roadmap step 4 (D4), outside this task. Integer-like keys still enumerate numerically under JavaScript rules. Deterministic diff consumers can sort explicitly when they require sorted keys.
- Preserve MCP's agent-facing default for non-runner calls and existing unrelated explicit truncation behavior. The runner's unbounded remote-model default changes both browser and board model reads because their path grammar is identical; it does not alter ordinary calls.

## Acceptance Criteria

- [ ] A context loss during an invoked browser page model yields `Error [page-navigated]: ...`; the separate opt-in yields `{ navigated: true }`, without consuming or changing model arguments. Other errors and timeout behavior remain intact.
- [ ] A reported inner length cut becomes `result-truncated`, naming the limit and `maxLength`; raised limit returns complete data. Runner model reads default to the existing unbounded constant; an explicit limit is respected. Structural limits are accurately documented.
- [ ] Browser page-model replies preserve insertion order for non-integer keys, including nested objects, by serializing the response before CDP by-value transfer. `editor.evaluate` retains its existing semantics; integer-like keys follow JavaScript enumeration rules.
