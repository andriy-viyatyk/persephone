# US-1538: Main owns the board trust and URL-mask snapshots

## Goal

Make the Electron main process the sole authority for board trust, module-service eligibility, and browser URL-mask claims. Load that authority before any restored renderer can start a service, and keep each window's renderer trust store synchronized with main.

## Background

Current source confirms each renderer creates and sends whole snapshots. `src/renderer/api/board-trust-sync.ts` builds `TrustedBoardSnapshotEntry` values from trusted roots plus bundled boards and sends them over `Endpoint.syncTrustedBoardSnapshot`; its module counter is initialized with `Date.now()` (`:25`) and the permission normalization call at `:38` discards its result. `src/renderer/editors/board/custom-editor-registry.ts` has the same clock seed for URL-mask snapshots (`:275`), and `refresh()` sends claims over `Endpoint.syncBrowserUrlMaskSnapshot` (`:535-543`). Main accepts the greatest generation in `src/main/module-service-supervisor.ts:130-139` and `src/main/download-service.ts:54-63`.

The pre-fix stale-generation drift hypothesis is specific: main keeps one global maximum (`module-service-supervisor.ts:131`), while each renderer seeds its own counter with its own `Date.now()` (`board-trust-sync.ts:25`). If window B is opened later, its base can exceed window A's. An untrust in A sends `base_A + k`, which is lower than B's last accepted generation `base_B + m`, so main silently drops A's revocation and leaves the service running. **Reproduced live before the fix (2026-09-28, Claude over MCP):** with the US1534Demo scratch board's service running (pid 22644), a second window was opened (`app.window.openNew()`), then `windows[0].boards.unregisterBoard(root)` was called. The trust file lost the root and window 0 reported `trusted: false`, but the service stayed `running` with the same pid after 15+ s, and window 1 still reported `trusted: true` (no cross-window broadcast). Both halves of the defect — dropped revocation and stale per-window trust — are confirmed. The cold-start `trust-not-ready` finding was also observed on this run's app instance: the restored `mem://us1536/*` pages had empty content and the "Provider demo/mem ... is unavailable" toast.

The trust file is `path.join(app.getPath("userData"), "data", "trustedBoards.txt")`, one absolute root per line, original path casing. This is visible in `src/main/utils.ts:40-43` (`getDataFolder`) and `src/renderer/api/board-trust.ts:1-8, 24, 51-54, 115, 127`; the file comment's extra `persephone/` segment is stale. Today renderer `BoardTrust.trust()` / `untrust()` persist it via `fs.saveDataFile()` and only update that renderer's `TGlobalState`; `subscribePaths()` is in-memory only (`board-trust.ts:77-94`). There is no main-to-renderer trust broadcast.

Cold-start ordering verifies the reported failure: `src/renderer.ts:8-17` awaits `app.initPages()` (restores persisted pages) before `app.initEvents()`. `src/renderer/api/app.ts:278-287` starts `initBoardTrustSync()` during events, after restored board-provider pages can request their service. In main, `ModuleServiceSupervisor.requireRecord()` throws `ServiceError("trust-not-ready")` if `trustedSnapshot` is absent (`src/main/module-service-supervisor.ts:408-410`). `setupMainProcess()` runs before `app`'s ready event and before `openWindows.restoreState()` creates renderer windows (`src/main/main-setup.ts:31`, `:115-122`), which provides a main-owned initialization point.

URL-mask claims are derived from local sources. `CustomEditorRegistry.refresh()` takes trusted roots in persisted list order, then enabled bundled roots in bundled registry order, reading each root's `board-manifest.json`; bridge-incompatible sources are skipped before mask ownership. The first source to claim each normalized mask wins (`src/renderer/editors/board/custom-editor-registry.ts:315, 331-369`). The trusted order is the newline order preserved by `parseTrustedPaths()` in `src/renderer/api/board-trust.ts:38-39, 54`; the bundled registry sorts records by `id.localeCompare()` at `src/renderer/editors/board/bundled-board-registry.ts:62`. Main must reproduce **trusted-list order first, then enabled bundled order sorted by id**, with first-owner-wins unchanged. Bundled assets are enumerated from `<appRoot>/assets/boards` (`bundled-board-registry.ts:41-62`).

Main must not read `appSettings.json`; `src/main/open-windows.ts:89-95` explicitly documents that main never loads it, and existing settings reach main through renderer IPC (`api.setMainScriptsEnabled` / `api.setMcpEnabled`, wired in `src/renderer/api/app.ts:292-298, 345-352`). Instead, each renderer pushes `disabled-bundled-boards` through `api.setDisabledBundledBoards(ids)` after settings are ready and whenever that key changes; `CustomEditorRegistry` already observes the setting at `src/renderer/editors/board/custom-editor-registry.ts:287-288`. Main starts with an empty disabled-ID set until the first renderer push. To keep this window short, `src/renderer.ts` must await settings and push the current value before `app.initPages()` restores pages. The remaining interval before that first renderer bootstrap can only affect download interception for disabled bundled boards; it does not alter trust or service authorization. Settings are shared from one file, so the push contains a setting value, never trust roots or derived claims.

Trusted-board manifest edits have no filesystem watcher today. The custom-editor registry rebuilds on trust changes, bundled registry notifications, and `disabled-bundled-boards` changes (`custom-editor-registry.ts:281-288`); the only explicit `customEditorRegistry.refresh()` call outside initialization/subscriptions is after Board Info registration (`BoardInfoEditorModel.ts:659`), which follows the trust mutation. Bundled assets are static during an app run and the bundled registry is only initialized/refreshed through `ensureInitialized()` in current callers. Therefore main recomputes on every trust mutation and on the pushed disabled-ID setting; those cover today's manifest refresh routes without a generic source-changed message. A newly added future renderer-only refresh route must explicitly request main recomputation.

Board trust changes already trigger prompt renderer cleanup: `customEditorRegistry` subscribes to `boardTrust.subscribePaths()` and rebuilds registrations (`custom-editor-registry.ts:281-282, 309-310`), replacing provider declarations and unregistering board-owned providers/schemes/capabilities during refresh. Its callers include `board-access.ts`, which subscribes to both trust and bundled-registry changes. Main trust updates must therefore broadcast the authoritative paths to every renderer, including the writer, so this established cleanup path runs in all windows.

Existing IPC is request/reply via `Endpoint` and `bindEndpoint()` (`src/ipc/api-types.ts`, `src/ipc/main/board-handlers.ts`); main-to-all-open-windows events use `openWindows.send()` (`src/main/open-windows.ts:24-28`) and typed `EventEndpoint` / `RendererEventObject` (`src/ipc/api-types.ts:334+`, `src/ipc/renderer/renderer-events.ts`). These are the patterns to extend.

### Before → after

Before, each renderer authors and races whole snapshots, and concurrent renderer file writes can also overwrite each other's trust changes:

```ts
let snapshotGeneration = Date.now();
await api.syncTrustedBoardSnapshot({ generation: ++snapshotGeneration, boards });
```

After, the renderer requests one trust mutation after the user-facing trust flow; main serializes the change, atomically replaces the file, applies service state, updates masks, then broadcasts authoritative paths:

```ts
await api.setBoardTrust(boardRoot, false);
// main reads, atomically mutates, applies service state, broadcasts, awaits stop, then replies
```

  every page loaded provider content, service `running`.
- **URL masks:** main-derived claims (`downloadService.browserUrlMaskClaims`) are the torrent-viewer
  masks — the only trusted or bundled manifest declaring `browserUrlMasks`, so equivalent to before.

**Not verified:** the `disabled-bundled-boards` push (no bundled board currently declares

## Concerns / Open questions (resolved)

- **Can main compute URL masks? Resolved: yes, with one pushed setting.** Main reads trusted paths and manifests, enumerates bundled assets, and uses renderer-pushed `disabled-bundled-boards` IDs. Main never parses `appSettings.json`. Before the first setting push, the disabled-ID set is empty; `src/renderer.ts` pushes after `settings.wait()` and before page restore, so the short earlier interval can only affect download interception for a disabled bundled board. Main preserves trusted-list order first, then enabled bundled order sorted by ID, with first-owner-wins collisions.
- **Trust writer and source of truth. Resolved:** main owns the trust file as well as the snapshot. Renderer trust UI still obtains the user's approval, then sends only the requested root and trust/untrust boolean. Main serializes read-modify-write operations and returns/broadcasts its resulting path list. This prevents two renderer windows from racing file writes as well as preventing stale snapshots from restoring trust. The board/script-facing APIs still cannot silently self-trust.
- **Cold-start readiness. Resolved:** initialize main before restored windows are created and gate every service entry point on the same initialization promise. Renderer bootstrap pushes disabled bundled IDs and fetches trust before page restore. The short interval before the first setting push has only the mask-interception effect described above.
- **Untrust completion. Resolved:** main applies the new supervisor snapshot, which synchronously initiates each untrust stop, rejects requests, settles storage, and fails/removes leases in `stopRecord()` (`src/main/module-service-supervisor.ts:747-777`). It broadcasts authoritative paths immediately after those actions begin, then awaits every stop promise before replying. Each stop waits for graceful shutdown or the 2-second kill deadline and stopped status. Provider/scheme/capability cleanup is initiated by the trust broadcast; renderer subscriptions run asynchronously and have no cross-window acknowledgment, so the response guarantees service and lease shutdown, but only initiation—not completion—of provider cleanup in other windows.
- **Settings and manifest refreshes. Resolved:** each renderer pushes `disabled-bundled-boards` once after settings load and again when that key changes. Main recomputes URL masks from that value. There is no manifest filesystem watcher today; trusted manifests are reread on trust mutation and the explicit registration refresh at `src/renderer/editors/board-info/BoardInfoEditorModel.ts:659` (which immediately follows trust), while bundled assets are static during a run. No generic source-changed event or main settings-file read is added.
- **Atomic file readers. Resolved:** keep `src/main/mcp/ai-vision/board-guide-mounts.ts`'s direct file reader. A same-directory temp-file write plus rename preserves its synchronous read; renderer `readPaths()` is redirected to main. Neither reader can observe a partially written trust list.
- **Board bridge version. Resolved: no bump.** The board-visible bridge and module-service protocol do not change; this is a main/renderer IPC and lifecycle ownership correction.
- **Live verification access:** the existing MCP `call` root routes `windows[i]` to a specific renderer and `app.boards.list()` exposes trust/service status. Each cycle creates a fresh auto-trusted copy with `app.boards.createDemoBoard(name, dir)` and uses `app.boards.unregisterBoard(root)` for untrust, avoiding unattended `boards.registerBoard()` dialogs. `mem://demo` is the Demo provider fixture.

## Acceptance Criteria

- Untrusting in one window awaits service stop and lease release before its IPC call resolves; its trust broadcast initiates provider/scheme/capability cleanup in all renderers, which must complete and remain effective after the other window's registry refresh. A renderer refresh cannot re-trust the board because no renderer submits snapshots. Verify through Persephone MCP `call` with two windows, twice.
- No trust or URL-mask generation counter is seeded from `Date.now()`; no renderer sends an authoritative trust or URL-mask snapshot.
- On cold restart with a restored board-provider page using `mem://`, main has loaded the persisted trust file before any service start/port request, and the page does not hit `ServiceError trust-not-ready`. Repeat the cold-restart MCP check twice.
- Every renderer's `boardTrust` state follows main broadcasts, and its existing subscriptions refresh UI access, custom-editor registrations, and provider/scheme/capability cleanup.
- URL-mask behavior remains equivalent: trusted and enabled bundled manifests contribute normalized claims, compatibility filtering and duplicate ownership order remain unchanged, and download interception uses only main-derived claims.
- Trust remains persisted at `<userData>/data/trustedBoards.txt` as newline-separated original-case paths. Main writes with a same-directory temporary file followed by rename, so direct readers never see a partial list; renderer IPC carries only a requested root/boolean and returns the authoritative paths after service application.
- The existing service permission gate (`permissions` includes `service` and board is trusted/bundled) and untrust stop reason remain intact.
- `BOARD_BRIDGE_VERSION` remains unchanged because no board-visible contract changes.
- Live verification uses Persephone MCP with two windows and records results for each changed path at least twice, including one full cold restart with a restored provider page.
