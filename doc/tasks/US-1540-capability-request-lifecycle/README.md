# US-1540: One owner for a capability request's lifecycle

## Goal

Give each capability request one lifecycle owner so deadline, trust revocation, caller cancellation, settlement, and at-most-once delivery have one authoritative implementation. Preserve EPIC-108 D6's page-scoped chain and D9's settlement contract while fixing cold-open handshake ordering and the concurrency mismatch.

## Background

US-1540 is [EPIC-115](../../epics/EPIC-115.md#us-1540-one-owner-for-a-capability-requests-lifecycle), Phase 2, size L, and follows [US-1539](../US-1539-capability-contract/README.md). EPIC-115 evidence names commit `693f3358`; the current source below was rechecked after US-1534, US-1539, and US-1544 landed. The EPIC-115 entry in `doc/active-work.md` links here and remains unchecked.

### Settlement contract to preserve

EPIC-108 D9 (`doc/epics/EPIC-108.md`, D9) defines these terminal outcomes: handler-board untrust settles `untrusted` and releases its pending intent; handler page/frame teardown settles `handler-closed` and releases that page's chain; caller-page close settles `cancelled` and sends `cancel`; deadline settles `timeout` and sends `cancel`; at-most-once means no platform redelivery; and every terminal case removes its pending record, with repeated settlement a no-op. D6 keeps `chain` and `depth` on the handler page while inbound requests remain unsettled, inherits the most recent unsettled chain for calls from that page, and removes the chain when that request settles. D6 intentionally notes that unrelated calls made during a handler's active request can inherit its chain.

### Verified current ownership and route

- `src/renderer/api/capability-bus.ts` has `CapabilityBus.pending` and `outstandingByHandler`. It assigns `deadlineAt`, installs the caller abort/page-disposal listeners and the renderer deadline timer, owns trust revocation through `subscribeBoardPermission`, settles terminal outcomes idempotently, and cancels through `transport.cancel()` (`CapabilityBus.invoke`, `settleRecord`, `settlePageRequests`, `settleUntrustedRequests`). It also creates request IDs, checks the handler trust, checks the caller page's D6 chain/cycle/depth, enforces payload size and the 32 outstanding-per-handler ceiling.
- `src/renderer/api/board-capability-transport.ts` has a second `pending` table, a second trust subscription, dispatch duplicate guard, trust checks before and at frame dispatch, handler-page disposal subscription and handler-closed settlement. It stores `pageChains` as `Map<pageId, Map<requestId, {chain, depth}>>`, including each unsettled inbound request. Its `chainForPage()` iterates active entries and returns the last one encountered; map insertion order therefore determines the current chain when concurrent requests are active. Under the selected single-slot model this becomes one `{ requestId, chain, depth } | undefined` per page.
- `src/renderer/editors/board/BoardWebview.ts` has a third `pendingCapability` table with request deadline timers, request-duplicate guard, trust subscription, cancellation/result routing and frame-generation checks. It passes the script request into `invokeCapabilityOutcome()` with this handler page ID and the caller-provided deadline (`handleCapabilityInvoke`). `src/renderer/api/capabilities.ts` now shares resolution through `invokeCapabilityOutcome()`; scripts flatten its board outcome once in `capabilities.invoke()`.
- Initial intent currently travels through `PagesLifecycleModel.openBoardHandlerPage()`: the generic route passes it through `openFile(..., { intent })`, while the bundled content-host route passes it to `addBundledBoardPage()`. Both rely on `setInitialBoardIntent()` and optional duck-typed `setInitialIntent` calls. The transport also uses optional `clearInitialIntent`, sweeps `boardPagesForRoot(root)` on settlement, and maintains `openingPages` to serialize empty-root opens. `BoardWebview` advertises `peekInitialIntent()` during frame init and tracks `initialIntentIds` to prevent reposting. The shim init branch accepts `data.intent` only if `!activeIntent`; a pre-handshake `capabilities:intent` can therefore occupy the slot and make the initial init intent disappear.
- `src/shared/board-bridge-version.ts` currently exports `BOARD_BRIDGE_VERSION = "1.19.0"`. Board-visible differences must be evaluated against this current version per EPIC-115's standing rule.

### Handler concurrency evidence

- The shim exposes a single `activeIntent` through both `persephone.intent.get()` and the legacy `persephone.intent.resolve/reject` calls (`src/board-shim.ts:662, 1640-1657`). `persephone.intent.onRequest()` delivers that one request to registered callbacks (`:719-730`). A second request currently receives `busy` while that slot is unsettled (`:1141-1156`).
- Bundled Excalidraw has one `handleCapabilityIntent(intent)` that switches on `image.edit` / `diagram.edit` and mutates one shared scene (`assets/boards/excalidraw/index.html:751-820, 850-854`). It has no independent per-request editor contexts. The Demo handler uses a request-bound callback and deduplicates IDs because both `onRequest` and `get()` can expose the active request (`assets/demo-board/app.js:27-49`). The guide example follows the same one-request pattern (`assets/guides/agents/boards.md:495-514`).
- No sibling `C:/projects/persephone-boards/boards/**` capability `onRequest` handler was found outside vendored libraries; the torrent viewer consumes provider APIs. The sibling repo therefore provides no existing concurrent-intent consumer to justify a multi-context shim.
- **Selected model: single-slot frame with a FIFO queue per handler page in the renderer transport.** It matches the public single-active-intent API and current shipped handlers, preserves the 32 outstanding limit as a bound on queued plus active work, and avoids teaching handlers to multiplex mutable UI state. The shim retains one context; transport dispatches the next queued request only after the active request settles or is cancelled. No request under the limit receives frame-level `busy`; `busy` remains the bus response when outstanding work reaches 32.

### Current route and handshake findings

- `BoardCapabilityTransport.resolveHandler()` selects/reuses a page or calls `PagesLifecycleModel.openBoardHandlerPage(root, title, intent)`; `openingPages` serializes concurrent cold opens by normalized root (`src/renderer/api/board-capability-transport.ts:105-123, 173-240`). The current workaround waits on the opening request's settlement, not on a reusable explicit frame-ready signal.
- `BoardWebview.transferPort()` sends `BoardPortInitMsg` with `model.peekInitialIntent()`, tracks its ID in `initialIntentIds`, and consumes the model value after `postMessage()` (`src/renderer/editors/board/BoardWebview.ts:367-397`). `handleLoad()` registers the capability frame before the port transfer/init handshake (`:405-438`), which is the US-1534 race. The shim's init listener processes its message synchronously, including adopting the initial intent before returning (`src/board-shim.ts:1032-1068`). Messages posted by the same source to the same target are delivered in order, so making the current-generation frame ready immediately after the init `postMessage()` succeeds ensures a later `capabilities:intent` is processed after init. No shim acknowledgment is needed.
- `PagesLifecycleModel` stores intent by a duck-typed editor call, `PageNavigator` repeats that cast, `BoardEditorModel` owns the `initialIntent` field, and the transport clears that field directly or sweeps all pages under a root (`src/renderer/api/pages/PagesLifecycleModel.ts:54-60, 313-331, 568-610`; `src/renderer/api/pages/PageNavigator.ts:43, 258-259`; `src/renderer/editors/board/BoardEditorModel.ts:209, 246-265`; `src/renderer/api/board-capability-transport.ts:71-80, 331-334`).
- The cold-open reservation must exist before calling `openBoardHandlerPage()`: that method is async and awaits source-pipe creation/opening before its page-created callback can provide a page ID. A page-ID route published only from that callback leaves a gap in which a second cold call could open a duplicate page.
- `boards.openBoard(boardRoot, { intent })` currently sends intent metadata through `openRawLink` to `open-handler.ts`, which opens the board through `PagesLifecycleModel.openFile()` (`src/renderer/api/boards.ts:283-295`; `src/renderer/content/open-handler.ts:20-25, 88-106`). The public API is `Promise<void>` and returns no capability result. The adapter will preserve fire-and-forget behavior, open the board without intent, then invoke the exact board-origin registration through the bus. For ordinary declarations, transport's existing root lookup (`boardPagesForRoot(root)[0]`, `src/renderer/api/board-capability-transport.ts:185-191`) reuses the page that the link path just opened. Declarations marked `alwaysOpensNewPage` retain that declared fresh-page behavior.

### Before → after lifecycle sketch

```ts
// Before: bus, transport and BoardWebview each own a pending record/timer/settlement path.
CapabilityBus.pending.set(id, record);
BoardCapabilityTransport.pending.set(id, record);
BoardWebview.pendingCapability.set(id, record);

// After: the bus is the sole settlement record; transport owns only page routing/chain/queue.
CapabilityBus.pending.set(id, record); // single deadline, trust/caller cancellation, settle-once
transport.enqueue(handlerPageId, request); // no timeout/trust settlement of its own
frame.dispatch(request); // wire send, active only after the init post succeeds
```

```ts
// Before: PagesLifecycleModel/BoardEditorModel own the initial intent and transport clears by casts.
model.setInitialIntent(intent);
// After: transport owns the exact page association; BoardWebview consumes it during init.
transport.initialIntentByPage.set(page.id, pendingRequest);
const initial = transport.takeInitialIntent(pageId);
```

## Concerns / Open questions

- Cold-open reservation: it must be created synchronously in transport.dispatch() before any await. The page-created callback binds that same reservation to the page ID. If opening throws or returns no page, the opener's dispatch promise rejects and each queued follower receives the same code/message; no follower tries an identical failing open.
- Single-slot queue and D6: keep one { requestId, chain, depth } per page, set only when a request is delivered to the frame and cleared on settlement/cancellation. Queued requests do not replace the active chain, preserving D6's rule that unrelated calls from the active handler inherit its chain.
- Reply routing and lifecycle ownership: the transport needs a per-request page/resolver/rejecter record so the dispatch promise can be settled from handler replies. This route record has no timer, trust subscription, duplicate guard, or lifecycle decision. The bus owns every terminal classification and request settlement.
- Page/frame teardown: a page.disposed routing notification rejects its active and queued dispatch promises as handler-closed with “The capability handler page was closed.” A frame reload/load error/init-post failure rejects only the active request as crashed; queued requests wait for the next current-generation frame to become ready.
- Init ordering: readiness is set for the current generation immediately after transferPort() successfully posts the init message containing the taken initial intent. Same-source/same-target message ordering plus the synchronous shim init listener puts later intent messages after init; no acknowledgment wire type is required.
- Cancellation batch ordering: when untrust or window closing cancels several requests on one page, do not dispatch a queued request between bus cancellations. Advance the queue after the bus's synchronous cancellation batch (for example, via a microtask) so a revoked handler never receives another queued intent.
- Deprecated legacy inputs: retain both public openBoard({ intent }) and ILinkData.intent now, with root-specific registration lookup and fire-and-forget bus invocation. The only decision for a later release is whether to delete these deprecated inputs.
- Trust boundary: the bus owns trust revocation for a selected handler and settles its in-flight requests. BoardWebview still must check that the calling board itself is trusted before allowing that board to list or invoke capabilities; that is caller authorization, not a second settlement owner. Preserve its AiVision trust cleanup when removing capability settlement from the shared trust listener.
- Bridge compatibility: the chosen model changes when concurrent requests receive service and changes the timeout message boards observe. Follow EPIC-115's bridge-version standing rule and bump minor to 1.20.0; document the bridge-visible outcome explicitly. Keep the separate board lifecycle busy flag (setBoardBusy) distinct from capability error code busy.

## Decisions

- Concurrency: use a single active intent context per frame with a FIFO queue in the renderer transport, scoped to the handler page. This matches persephone.intent.get() and the request-bound handler patterns in Excalidraw, Demo, and the board guides. A second concurrent intent below 32 waits and is then delivered; the 33rd outstanding invocation rejects at the bus with busy. Do not add a shim context map.
- Lifecycle invariant: every bus-originated termination (timeout, caller page disposal, abort, untrust, or renderer window closing) calls transport.cancel(registration, requestId) exactly once. The transport silently removes a queued request, or, for the active request, posts capabilities:intent:cancel, clears that page's D6 chain, and schedules the next queued request after the synchronous cancellation batch. Cancellation never resolves or rejects the transport dispatch promise.
- Handler outcomes: result, rejected, handler-closed on handler-page disposal, crashed on frame reload/load error/init-post failure, and rejected DataCloneError reach the bus only by settling the transport dispatch() promise. The transport keeps a per-request routing record containing the page and dispatch-promise resolver/rejecter; this is routing state, not a lifecycle table, and owns no timer, trust subscription, duplicate guard, or terminal policy.
- Handler page/frame teardown: a page.disposed routing notification rejects the active dispatch promise and every queued dispatch promise for that page with handler-closed and “The capability handler page was closed.” Reload/load error/init-post failure rejects only the active request as crashed with the current failure message; queued requests remain in the page reservation and dispatch to the next ready generation.
- D6 chain: because each page has at most one active request, keep one optional { requestId, chain, depth } entry per page. Set it immediately before delivery to the frame; clear it on handler outcome or bus cancellation. Queued work does not change the active chain, so unrelated invokes from the active handler still inherit that chain.
- Initial intent and cold open: create one normalized-root opening reservation synchronously in transport.dispatch() before its first await. It owns the FIFO before a page ID exists. The lifecycle's page-created hook binds the same reservation object to the page ID before mount; BoardWebview takes the initial intent while composing BoardPortInitMsg. If opening throws or returns no page, reject the opener through its dispatch promise and reject queued followers with the same code/message. alwaysOpensNewPage calls use independent pages and do not join this reservation.
- Init readiness: BoardWebview marks a generation ready immediately after transferPort() successfully posts the init message with the taken initial intent. handleLoad resets readiness for each new generation. The shim's init listener is synchronous, and same-source/same-target postMessage ordering delivers any later intent after init, so no readiness acknowledgment message or shim readiness change is needed.
- boards.openBoard({ intent }): keep the deprecated public option as a root-specific fire-and-forget adapter. Open the named board without an intent through the existing openRawLink path, then invoke the matching board-origin registration with capabilityBus.invoke(); ignore the legacy requestId and warn if no matching declaration or invocation failure occurs. The existing open-handler ILinkData.intent path also opens without forwarding intent into page lifecycle options, then invokes the same helper. openRawLink reaches open-handler and opens the board page; the subsequent transport lookup of boardPagesForRoot(root)[0] reuses that page. Keep both deprecated inputs in this story; deciding whether to remove them is deferred.
- BOARD_BRIDGE_VERSION: bump 1.19.0 to 1.20.0. Boards observe serial processing of concurrent intents below the limit, busy only at the 32-request bus cap, and one canonical timeout message (“Capability invocation deadline elapsed.”). There is no new init-ready wire message.
- No result-shape change: script callers keep the existing projected values and board callers keep { pageId?, result? }; cancellation/error codes remain the existing CapabilityErrorCode set. The standalone board busy-state handshake is unchanged.

## Acceptance criteria

- The bus is the only owner of per-request deadline, trust, caller cancellation, pending settlement, and at-most-once delivery/cancellation; only one deadline timer can reject a request.
- For one request, deadline, trust revocation, caller close, handler close, and frame teardown produce one terminal result and release the bus record, queue slot, and D6 page chain. Repeated terminal signals do nothing.
- D9 is preserved: untrust → untrusted; handler page/frame close → handler-closed; caller page close → cancelled plus cancel; deadline → timeout plus cancel; no redelivery; no pending entry survives settlement.
- A synchronous normalized-root opening reservation exists before the first async open work starts. Two simultaneous first invocations that arrive before a page ID exists join its FIFO, one page is opened, and its page-created callback binds the same reservation before mount. If opening fails, the opener and all queued followers reject with the same code/message.
- A frame generation becomes ready immediately after its init post succeeds; queued non-initial requests are posted only after that point. Reload resets readiness; only the active request rejects crashed and queued requests wait for the new generation.
- A single frame processes at most one unsettled intent. Concurrent calls up to the 32-per-handler limit resolve in order; the 33rd outstanding call rejects with busy at the bus.
- D6 cycle/depth behavior remains page-scoped with one optional request/chain/depth entry per page; it is set on delivery and cleared on settlement/cancellation.
- Every bus-originated termination calls transport.cancel() once; cancellation removes queued work or cancels the active frame request and advances the queue without the transport settling the dispatch promise. Handler outcomes reach the bus only through the transport dispatch promise. Handler page disposal rejects active and queued requests as handler-closed; frame reload/error/init-post failure rejects only the active request as crashed.
- The shim rejects unexpected overlapping wire delivery with code rejected and message “The board is already serving a capability request.” It uses a per-context delivered flag so a late onRequest registration can receive the active intent once.
- The transport initial-intent map is keyed by page ID and is consumed once by the handshake. BoardEditorModel.initialIntent, both duck-typed casts, the per-root clear sweep, openingPages, and BoardWebview.initialIntentIds are removed.
- boards.openBoard({ intent }) and ILinkData.intent remain deprecated, named-board fire-and-forget adapters through capabilityBus.invoke(); caller requestId is ignored, missing declarations/failures warn, and open-handler's just-opened page is reused by transport.
- BOARD_BRIDGE_VERSION is 1.20.0, and board guides document serialized concurrency, the existing 32-call busy ceiling, and the canonical timeout text. No bridge message is added for readiness.
- Every live case in the verification plan passes twice for both script and board callers where the caller remains observable, including two concurrent cold calls with no handler page open.

## Live verification results (2026-09-28)

Run against the dev app after a cold restart, over the Persephone MCP, with the trusted scratch board `US1534Demo` (`demo.greet`) as the handler and a scratch caller board (created, then untrusted and deleted) as the board caller. Every case ran twice.

| Case | Script caller | Board caller |
|---|---|---|
| Resolved / primitive | `{ greeting, requestId, received, pageId }` / `{ pageId }` | `{ pageId, result }` / `{ pageId, result: "plain-board friend" }` |
| Rejected | `rejected` "demo rejected" | `rejected` "demo rejected" (`BoardCapabilityError`) |
| Timeout | `timeout` "Capability invocation deadline elapsed." | same code and text (one message now) |
| Cancelled (abort signal; caller page closed) | `cancelled` "Capability invocation was cancelled." / "The caller page was disposed."; the queued request behind it then resolved | — (a board caller's own page cannot outlive its frame) |
| Untrusted mid-request | active and queued both `untrusted` "The capability handler board is no longer trusted."; while untrusted, `no-handler` | active and queued both `untrusted`, same text |
| Handler page closed mid-request | active and queued both `handler-closed` "The capability handler page was closed." | same |
| Concurrent cold calls, no handler page open | three calls → one page, all resolved in order | three calls → one page, all resolved |

Observed deviation from the plan: when the named board already has a page open, the legacy `openBoard({ intent })` path opens a further page (the pre-existing `openBoard` behaviour for a non-single-instance board), and the intent is delivered to the page the transport already routes to, not to the new page. The route is deprecated and fire-and-forget, so this is recorded rather than changed.
