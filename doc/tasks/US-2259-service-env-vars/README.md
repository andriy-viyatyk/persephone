# US-2259: Env vars in board services

[EPIC-219: SSH board](../../epics/EPIC-219.md) - Implemented (unreviewed)

## Goal

Let a trusted board's host-managed module service read and update its own board environment variables without a board page open. This lets the SSH service restore connections and credentials from the shared env store, including re-reading the writable flag before writes.

## Background

- `src/board-shim/shared-state-api.ts` exposes page `var.get(name, env?)`, `set(name, value, env?)`, `list(env?)`, and `show()`. `src/ipc/board-bridge/frame-protocol.ts` and `src/renderer/editors/board/frame/board-host-router.ts` mirror those four. There is **no** page `delete` or `keys` today. Retain `list` and `show`, add `delete` and `keys` to the page as well as the service, and make `keys(env?)` identical to `list(env?)`. This preserves existing boards and gives both contexts the requested names.
- `src/renderer/editors/board/frame/settings-and-vars-bridge.ts` resolves the root via `resolveBoardNamespace` and invokes `resolveBoardVarRequest` in `src/renderer/api/board-vars/board-vars-bridge.ts`. Its `SerialQueue` serializes load, prompt and access within a renderer. `src/renderer/api/board-vars/BoardEnvStore.ts` uses the configured `board-vars.file`, restores/decrypts a `TextFileModel`, parses on load, and saves through that model so encrypted files stay encrypted. Missing values return `undefined`; lists return names only. Omitted or empty `env` uses the `default` profile; get/set currently coerce names and values using `String(value ?? "")`. `set` returns void. `show` opens the editor and is page-only.
- `src/renderer/api/board-vars/admin-api.ts` exposes unrestricted `app.boardVars` to trusted scripts; its `namespaceFor` delegates to `src/renderer/api/boards/board-namespace.ts`. That resolver reads the manifest and registry on each call and uses `boardIdentity`: trimmed nonempty author and name become `author/name`; otherwise a bundled board uses `bundled:<folder-id>`, and a local board uses its root path. Namespace collisions can be accepted at registration, so isolation is by resolved namespace, not a guarantee against intentionally accepted identity collisions. Do not accept a root or namespace from service code.
- The existing service settings route starts at `src/module-service-host/service-api.ts` and `src/module-service-host/main-requests.ts`, through typed `board-settings-get` messages in `src/ipc/module-service-channels.ts` and `src/main/module-service/process.ts` to `ServiceBoardSettingsAdapter` in `src/main/module-service/board-settings-adapter.ts`. Main associates the process with `ServiceRecord.boardRoot`, checks current generation, running state and `isAllowed`, and supplies that root to the renderer RPC. `src/renderer/api/board-service-settings.ts` validates root/trust/manifest before handling `serviceSettingsGet`; `src/renderer/api/renderer-rpc-bootstrap.ts` registers it. `src/main/renderer-rpc.ts` and `src/ipc/renderer-rpc.ts` provide typed RPC, wire errors, `PendingRequests`, target checks and cancellation.
- Page var routes use `{ kind: "trusted" }`, with no EPIC-119 var-specific permission. Services already require trusted status and the `service` grant to start and use settings (`isBoardSettingsAllowed` in `src/main/module-service-supervisor.ts`); add no further var permission. The service is host-managed, not the raw protocol mode.
- `SERVICE_REQUEST_DEADLINE_MS` and the host's `CAPABILITY_DEFAULT_TIMEOUT_MS` are 10 seconds. Both `MainRequestFamily.request` and the main settings adapter currently impose that deadline; `requestRenderer` defaults to 30 seconds unless passed `RENDERER_REQUEST_NO_TIMEOUT`. `BoardEnvStore.ensureLoaded()` can show a password prompt and return `locked` on cancel or failed decrypt; the bridge can show the creation dialog and returns an error on decline. A valid user response may take longer than any of those deadlines.
- `selectBoardSettingsRenderer` currently selects the **first live entry in `openWindows.windows`**, not the focused window or the board page, and waits for `whenReady` and `did-finish-load` if loading. The adapter watches the selected webContents and fails in-flight requests on loss/reload; settings subscriptions have their own reinstallation logic. Per-renderer singleton queues do not serialize separate windows. `treeList` and `treeStat` have no outer provider deadline in `src/shared/provider-operation-policy.ts`; write operations have a 10-second outer deadline even if an inner var call can wait. The existing tree UI displays generic Loading; the creation/decrypt dialog identifies the env store, but the tree does not currently say it is waiting for it.

## Implementation Plan

- [x] **Page and store contract.** In `src/renderer/api/board-vars/BoardEnvStore.ts`, own `delete(namespace, name, env?)`: remove only that key in the selected profile, save via the existing cloned-object / `model.changeContent` / `saveFile` path, and make deletion of a missing key a successful no-op. Preserve other namespaces and profiles. In `board-vars-bridge.ts`, extend `resolveBoardVarRequest` with `delete` and `keys`, reuse `requestQueue`, `ensureLoaded`, `list` and `set` conventions, including string coercion and default profile. `keys` is an alias for `list`; both return `string[]` and do not expose values. Return void for deletion. Keep page `show` and `list` intact.

  ```ts
  // Before: page methods
  var: { get, set, list, show }
  // After: same existing methods plus
  var: { get, set, list, show, delete: remove, keys: list }
  ```

  Add typed `var.delete` and `var.keys` to `src/ipc/board-bridge/frame-protocol.ts`, trusted handlers in `src/renderer/editors/board/frame/board-host-router.ts`, method union in `settings-and-vars-bridge.ts`, and page methods in `src/board-shim/shared-state-api.ts`. Use the existing frame method maps and `hostFrame.request`, not a new frame protocol. Update any actual board-facing declarations found during implementation; `PersephoneHostApi` in `src/module-service-host/service-api.ts` is the existing service type, whereas `src/renderer/api/types/board-vars.d.ts` and its `assets/editor-types/board-vars.d.ts` copy describe the separate admin API and need no changes for these methods.
- [x] **Service request path.** Extend `src/ipc/module-service-channels.ts` with a typed `board-vars-request` (`requestId`, operation `get | set | delete | keys`, arguments only) and `board-vars-response` using the existing response error shape. No root/namespace travels from the service. In `src/module-service-host/main-requests.ts`, register the response in `RESPONSE_POLICIES` with the existing settings family and allow an explicit no-deadline option on `MainRequestFamily.request`; default remains 10 seconds for every existing caller, with the outstanding-request cap and `failAll` lifecycle intact. In `src/module-service-host/service-api.ts`, add the typed `var` object to `PersephoneHostApi`, `createServiceApi`, and `installServiceApi`; use that family and no-deadline option, reject raw protocol mode like settings, preserve optional `env` and page coercion semantics, and validate returned string/undefined, string array, and void shapes. Never log arguments or results.

  ```ts
  // Before: only settings uses the board-settings family
  settings.get(id) // board-settings-get, 10 s
  // After: same family and response machinery; no namespace parameter
  await persephone.var.set("SSH_CONNECTIONS", json);
  const json = await persephone.var.get("SSH_CONNECTIONS");
  const names = await persephone.var.keys();
  await persephone.var.delete("SSH_CONNECTIONS");
  ```

- [x] **Main and renderer ownership.** Route the new discriminant in `src/main/module-service/process.ts` through the existing settings adapter. Extend `ServiceBoardSettingsAdapter` in `src/main/module-service/board-settings-adapter.ts` to own var dispatch and error mapping, reusing its process-generation, `isAllowed`, abort-controller and response machinery. Add `serviceBoardVar` to `RendererRpcMethods` in `src/ipc/renderer-rpc.ts` with main-supplied `boardRoot`, operation and args. Add `src/renderer/api/board-service-vars.ts` as the renderer RPC handler owner; register it in `src/renderer/api/renderer-rpc-bootstrap.ts`. Extract the existing `validateBoardRoot` from `src/renderer/api/board-service-settings.ts` to a genuinely shared board-service validation module and use it in both handlers; it must continue to use `BoardRoot`, `boardRegistry` and `readBoardManifest`. Resolve the namespace using `resolveBoardNamespace(root)`, then invoke the same `resolveBoardVarRequest` queue as page calls. Convert its errors to coded errors without logging values. Use the existing wire-error path; no new correlator, ack, transport or error envelope.
- [x] **Waiting and lifecycle policy.** For var requests only, use no timer in both `MainRequestFamily`'s `PendingRequests` and the adapter's `requestRenderer(..., RENDERER_REQUEST_NO_TIMEOUT, signal)`; retain service stop, generation change, trust revocation and webContents loss cancellation. `src/shared/pending-requests.ts` owns timer semantics: pass zero: its `create` disables timers for non-positive values. Define stable codes `board-vars-declined` for a declined creation dialog or cancelled/failed decrypt, `board-vars-unavailable` for missing/unreadable/unparseable store or failed save, and `window-unavailable` when there is no live window or the selected renderer is lost/reloads. Extend the bridge reply to carry the code as well as its existing message; page calls retain their existing error messages and get the code, service errors survive `toWireError`/`fromWireError` and `MainRequestFamily.settleResponse`. Wrong-password and cancel are both `locked` today, so both map to declined; post-creation `not-configured` is unavailable. Keep `untrusted` and `service-exited` for their existing lifecycle cases. Catch failures from `ensureLoaded` as well as operation failures. Pass the renderer RPC abort signal into the queued var operation; check it before opening a dialog, after each awaited prompt/load and immediately before mutation so a cancelled queued request cannot later write. A save already in progress cannot be rolled back; never retry it automatically. Do not silently return missing values for these errors.
- [x] **Window choice and reload.** Reuse `selectBoardSettingsRenderer` in `src/main/module-service-supervisor.ts`: it selects the first live window, independent of focus or board page. Add abortable readiness/load waiting and listener cleanup at the existing selection/adapter boundary for var requests, reusing `onWebContentsGone` and the adapter's abort signal. Keep the supervisor from growing: if the readiness logic cannot be made abortable without growth, extract only that wait into a focused collaborator, not the selection rule. A request starting during load waits for readiness; a reload or disappearance after selection rejects with `window-unavailable` without retry. A later request may select the ready window; no live window rejects immediately. The renderer queue is per-window, so simultaneous page requests in different windows are not globally serialized. Avoid automatically retrying an uncertain `set` or `delete`.
- [x] **Outer deadlines.** `treeList` has no outer deadline in `src/shared/provider-operation-policy.ts`, so the first listing can wait for the store-creation or decrypt prompt. The dialog identifies the request and the tree's existing generic Loading state is sufficient. Write operations retain their 10-second end-to-end deadline; an inner var request does not extend it. A save already in progress cannot be rolled back.

## Concerns

- The page API discrepancy is resolved above by adding `keys` and `delete` to both contexts, keeping `list`/`show` backward compatible. Optional profiles match existing page semantics. `delete` is idempotent and returns void.
- Independent renderer stores and queues can race across windows on the same file; first-live selection keeps service requests on one renderer while it remains available but does not serialize page calls in other windows. Do not claim stronger isolation or reimplement a global store in this task. No automatic retries after uncertain writes.
- BT-104 is expected to cache connection records after the first read and re-read the writable flag with `var.get` before each write. An unlocked store is fast; if the store is locked, a write that waits on the prompt fails within its 10-second deadline with a coded timeout error, which is acceptable. Reject writes when the flag is disabled even if the tree has not refreshed. Never log secrets or include them in errors; manual epic exit tests use only `persephone-vm` and its containers.
- Do not use `await import()` or a wrapper just to bypass an import zone; fix dependency direction. No new protocol machinery; reuse typed messages, `requestRenderer`, `PendingRequests`, wire errors, namespace resolution, and existing registries. Do not grow any roadmap section 2.3 god file. Strict-folder null fixes are type-only unless separately recorded as a behavioral change.

## Acceptance Criteria

- [ ] A trusted, service-enabled board service can get, set, delete and enumerate its own profile's string vars without a board page; missing get is `undefined`, missing delete succeeds, and page `list` and new `keys` agree. Existing page methods remain compatible.
- [ ] Main, not service input, chooses the board root; renderer resolves the same namespace as `app.boardVars.namespaceFor`. Other distinct namespaces and profiles remain untouched, including under malformed requests.
- [ ] No additional var permission is required. Untrusted or stopped services cannot access the store; no secret appears in logs or errors.
- [ ] Creation and decryption prompts can remain open beyond 10 seconds; codes distinguish decline, store failure, and unavailable window. Stop/revocation/reload settle pending work and clean listeners; first-live-window and reload behavior match this plan.
- [ ] First tree listing can wait through the prompt with the existing generic Loading state and resumes or reports the error afterwards. Existing bounded write operations retain their deadlines.
- [ ] Bridge 1.67.0 and its history entry are present. Scripted UI tests cover service get/set/keys/delete without a page, foreign namespace isolation, page delete/keys/list, and one creation-dialog decline. Relevant typecheck, lint, UI tests and guide check pass. Epic-close guide work is recorded above.
