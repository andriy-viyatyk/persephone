# US-1735: “Translate to…” in the text editor

## Goal

Let a user translate the current Monaco selection or complete text page into a chosen language and open the translated text in a new Monaco page. The source page and its content remain unchanged.

## Background

EPIC-135 makes Persephone a consumer of `text.translate@1`; the renderer does not own a translation engine. The normative contract is [`assets/guides/agents/text-translate.md`](../../../assets/guides/agents/text-translate.md). It defines directed model pairs, language detection candidates, separate explicit download operations, per-item results, request progress, cancellation, and hard batch limits. `describe` reports direct model pairs only; a provider may route a request through English. `not-ready` means translation did not start and no model was downloaded.

The current uncommitted US-1734 change adds [`TextTranslationProvider`](../../../src/renderer/ui/translation/TextTranslationProvider.ts). Verified client methods are `list()`, `describe(provider, scope?)`, `detect(provider, text, htmlLang?, scope?)`, `translate(provider, batch, scope, onProgress?)`, `download(provider, from, to, scope, onProgress?)`, `cancelScope(scope)`, and `dispose()`. `list()` filters to version 1. Each operation opens a separate channel; `translate()` checks 32 items and 64,000 Unicode code points and unique keys. The client limits active translation channels to four and active channels per host board to 15 (leaving one of the platform's 16 channel slots for control operations), queues the rest, reports translate and download progress, and cancels a single operation or every operation in a local scope. The contract's 1 MiB serialized-message ceiling is additionally enforced by [`TranslationServiceChannel`](../../../src/renderer/ui/translation/TranslationServiceChannel.ts). The provider board is being implemented in parallel in persephone-boards, so the consumer must treat provider descriptions and operation replies as runtime data and surface contract errors.

Monaco toolbar additions are composed in [`src/renderer/editors/monaco/index.ts`](../../../src/renderer/editors/monaco/index.ts). US-1731's Transcript contribution is a direct pattern: `TranscriptToolbarContributionView` queries `speech.transcribe` version 1 during mount, listens for board trust changes, and hides its root while unavailable and idle. The view owns the toolbar button and a UIKit `MenuView`; its `TranscriptController` owns provider interaction and lifecycle. The toolbar is inserted through `TextChromeView`'s `rightToolbarContributions` slot. Monaco editor actions are registered in `MonacoBodyView.onHostMount` with `ed.addAction()` by setup helpers such as `setupRichPaste()` and `setupWordWrapAction()`, and their returned disposers are included in `hostCleanups` and invoked when the host changes or is disposed. This is the correct editor-text context-menu hook. No `contextMenuGroupId` is currently used in `src/renderer/editors/monaco/`; the installed Monaco API declares `contextMenuGroupId`, `contextMenuOrder`, and action preconditions, and Monaco's menu service sorts `navigation` first, then groups lexically, and then `contextMenuOrder`. Its documented defaults are `navigation`, `1_modification`, and `9_cutcopypaste`; put this action in custom group `2_translation` with a stable order so it appears after modification actions and before cut/copy/paste. Page-tab context menus are a different surface: `EditorModel.onGetMenuItems()` feeds the tab's right-click menu, not the editor text context menu.

**Entry-point decision:** use a Monaco toolbar button with a small UIKit menu for **Translate selection** and **Translate page**, alongside Transcript in the right-toolbar contributions. Also register a Monaco editor action **Translate selection…** in `MonacoBodyView` using `ed.addAction()`, `contextMenuGroupId: "2_translation"`, and `contextMenuOrder: 1`. Give it preconditions for `editorHasSelection`, a supported editor language (`plaintext` or `markdown`), and a custom provider-availability context key updated from the same version-1 provider/trust state as the toolbar. Its `run` opens the same flow in selection mode. Do not add a keyboard shortcut or a command-palette-only action. Hide the toolbar and context-menu action when no compatible `text.translate@1` provider is available, following Transcript's version-1 provider check and trust-change refresh. The selection precondition hides the action unless Monaco has a nonempty selection.

The supported v1 source formats are Monaco language id `plaintext` and `markdown`. Code language ids are out of scope: hide/disable the translation entry for other language ids rather than translating comments or identifiers accidentally. Markdown is identified by the host's language id, not the filename. The editor project already uses `remark-parse`, `remark-gfm`, `unified`, and `remark-rehype` in [`src/renderer/editors/markdown/MarkdownBlockView.ts`](../../../src/renderer/editors/markdown/MarkdownBlockView.ts); preserve source spelling by using Markdown AST positions to replace only eligible source spans, while protecting front matter explicitly (the renderer's current pipeline does not demonstrate front-matter parsing).

Pages are created through [`PagesModel.addEditorPage()`](../../../src/renderer/api/pages/PagesModel.ts), delegated to `PagesLifecycleModel.addEditorPage()`. That method validates the language and editor, creates a `TextFileModel` host with no `filePath`, sets the title/language/editor, initializes content, and adds a page. Supplying nonempty content calls `TextFileModel.changeContent()`, which marks the new host modified and unsaved; this is appropriate for an unsaved translated document and lets normal close/save prompts protect it. Use editor id `monaco`, retain the source's language id, and title it `<source title> (<target language name>)`. Never reuse the source host or its file path. A selection translation opens only the translated selection; a page translation opens the translated whole document.

Dialogs and user-visible messages belong to the app UI, not a new UIKit primitive. Compose existing UIKit `DialogView`, `SelectView`, `ButtonView`/`IconButtonView`, and `ProgressBarView` in a feature view under `src/renderer/ui/translation/`; use `ui.confirm()` for explicit download consent and `ui.notify()` for notices where a modal is not needed. The progress overlay exposed by `ui.showProgress()` has no cancel control, so the translation/download surface must retain an explicit cancel button wired to the returned `TranslationOperation.cancel()` and must close/cancel its scoped work on disposal. UIKit rules in [`src/renderer/uikit/CLAUDE.md`](../../../src/renderer/uikit/CLAUDE.md) require controlled values, `VanillaView` lifecycle ownership, data attributes, and `uikitText()` only for UIKit defaults. App copy must use `t()` and the flat English catalogs described in [`doc/standards/localization.md`](../../standards/localization.md).

## Implementation Plan

1. **Add the Monaco toolbar entry, editor context action, and provider availability gate.** In `src/renderer/editors/monaco/index.ts`, compose a translation controller and `TranslateTextToolbarContributionView` alongside `TranscriptController` and `TranscriptToolbarContributionView`, using the same `MonacoBodyView.getEditor()` callback and `TextChromeView.rightToolbarContributions` slot. Add `src/renderer/ui/translation/TranslateTextToolbarContributionView.ts` and a co-located stylesheet if needed. Reuse `TextTranslationProvider.list()` and filter version 1; refresh on the same board trust-change event as Transcript, hide while unavailable, and dispose the controller with the view. Pass the current language support and provider-availability state into `MonacoBodyView`; keep a Monaco editor context key synchronized with provider/trust availability so its action can be hidden as state changes. In `MonacoBodyView.onHostMount`, register a `setupTranslateSelectionAction()` alongside `setupRichPaste()` and `setupWordWrapAction()`, and add its disposer to `hostCleanups`. Its `ed.addAction()` precondition combines `editorHasSelection`, `editorLangId == plaintext || editorLangId == markdown`, and the custom availability key; use `contextMenuGroupId: "2_translation"` and `contextMenuOrder: 1`. The action label is **Translate selection…**, it has no keybinding, and its run invokes the same controller flow in selection mode. The toolbar menu offers separate selection/page actions; no keyboard shortcut or command-palette-only action is part of this task.

   Before → after shape:

   ```ts
   // Before: MonacoToolbarBitsView owns only the Transcript contribution.
   this.transcript = this.child(new TranscriptToolbarContributionView({ controller }));

   // After: the same toolbar view owns Transcript and the provider-gated Translate contribution.
   this.transcript = this.child(new TranscriptToolbarContributionView({ controller }));
   this.translate = this.child(new TranslateTextToolbarContributionView({ controller: translateController }));
   ```

2. **Build the picker and operation flow.** Add a controller/model and app-level dialog view under `src/renderer/ui/translation/` (suggested names: `TranslateTextPageController.ts`, `TranslateTextDialogView.ts`, and its stylesheet). On invocation, snapshot the source title, language id, full text, selected text/range, and a stable local scope derived from the source `PageModel.id`; do not retain mutable editor state as the translation result source. Discover the provider and call `describe`. Call `detect` once on a nonempty sample of at most 4,096 code points: selection mode samples the selection text; page mode samples the page text. For Markdown, classify protected source spans first and remove code, URLs/link destinations, front matter, and other non-translatable spans from the detection sample so code does not skew detection. Show the detected source and confidence. Put detector candidates first in the source dropdown, followed by every source code the provider describes as an `X → en` pair and `en` itself, deduplicated and sorted by display name. This lets the user correct a bad detector result even when the correct language was not among its candidates. Send the chosen `from` on every batch. If detection fails, show a translated error notice and let the user retry or cancel; the described source-language choices remain available for manual correction.

   Get the app UI language from `getActiveLocale()` in `src/shared/i18n/active-locale.ts`. `src/renderer/i18n/startup.ts` resolves the saved language setting (including `"auto"`) to a concrete active locale before setting it; pass that active locale, never the literal setting value `"auto"`, to `Intl.DisplayNames([getActiveLocale()], { type: "language" })`. Use the resulting display name with the language code as fallback. Do not use endonyms. In particular, use full script tags (`zh-Hans`, `zh-Hant`) so `Intl.DisplayNames` produces distinct names such as “Simplified Chinese” and “Traditional Chinese” in an English UI.

   Populate target languages from `description.pairs`: form available language codes from the described directed pairs, then rank choices with installed routes first and available routes after them. For a source/target route, prefer a direct `from → to` pair; otherwise recognize the contract's English pivot only when both `from → en` and `en → to` pairs are described. A route is installed only when all its required legs are installed; show the sum of the missing leg `sizeBytes` values for an available route. Exclude the same-language target. Do not claim arbitrary routes not represented by the description; handle `unsupported-language-pair` as a user-visible error if a provider rejects a route. Persist the selected target with `uiPreferences.readString()` / `write()` under a namespaced translation preference key after the user starts the operation; preselect it on the next invocation when still available. With no remembered target, preselect the app UI language when it differs from the detected source and is an offered route; otherwise preselect English when it differs from the detected source and is offered. If neither default is an offered route, leave the picker without an implicit unsupported choice and require the user to choose an offered target.

3. **Ask before downloading and report download progress.** If the selected route is not installed, use `ui.confirm()` with the computed missing-model size and explicit Download/Cancel buttons. On consent, call `TextTranslationProvider.download()` for the chosen source/target pair; the provider contract resolves pivot legs itself and reports each `leg` separately. Render its `loadedBytes` / `totalBytes` in the active dialog with a UIKit progress bar and expose Cancel wired to `operation.cancel()`. Do not start translation until `download-result` reports installed. Handle `download-failed`, `cancelled`, provider disconnects, and a stale `not-ready` response with localized notices; `not-ready` must re-enter the consent/download step because the contract forbids implicit downloads.

4. **Segment supported document text without damaging layout or syntax.** Add a pure translation segmentation/reconstruction module under `src/renderer/ui/translation/`.

   - For `plaintext`, split on blank-line paragraph boundaries while preserving every original delimiter and newline sequence. Keep indentation and leading list markers outside the translated span. Treat each paragraph/list item as one keyed item where possible; use `Intl.Segmenter` sentence boundaries to subdivide an oversized paragraph, recording source offsets so the result can be reassembled in original order and line layout.
   - For `markdown`, parse with the existing `remark-parse`/`remark-gfm` toolchain based on language id `markdown`. Preserve YAML/TOML front matter, fenced and indented code blocks, inline code, raw HTML, link destinations/URLs, image destinations, and all delimiters. Translate eligible prose text and link-label text only. Use AST source positions to replace eligible text spans in the original source rather than serializing the whole AST, retaining untouched Markdown exactly. Keep list markers and indentation outside translated text. A source-position span containing only whitespace or empty text is not sent.
   - For a Markdown selection, parse the full source document to classify eligible prose and protected spans, then intersect those AST source spans with the selected range. Use only the selected text for detection after removing protected intersections. Translate only selected intersections with eligible text; preserve selected syntax, code, URLs, and all bytes outside eligible intersections exactly. This avoids parsing an arbitrary selection fragment whose boundaries may split Markdown syntax.
   - Build keyed batches with no more than 32 items and no more than 64,000 Unicode code points total; split individual long paragraphs at sentence boundaries (then safe code-point boundaries as a last resort) so no one item exceeds the request budget. Keep the serialized open message below the contract's 1 MiB channel limit. The provider internally subdivides engine work at 8 items / 8,192 code units; the consumer need not mimic those engine limits. Limit local concurrent translate calls to four (already enforced by the client), preserve item order, and let the client's control channel slot remain available for describe/detect/download.

5. **Translate with progress, cancellation, and item-level errors.** For each batch, call `translate()` with the user-selected `from`, chosen `to`, `format: "text"` items, a stable local scope, and an `onProgress` handler. Update the dialog's aggregate completed/total count and progress bar. Keep a Cancel action available throughout translation; cancel the current operation and all queued/in-flight operations in the source-page scope, then close the dialog without opening output. Do not send a protocol `scope` field: scope exists only in the client and maps to each channel's cancel/close behavior. If the provider returns item-level failures, keep the original source span for those items, continue reconstructing successful siblings, and show one summary notice naming the failed item count; request-wide errors (including `too-large`, `unsupported-format`, `unsupported-language-pair`, and `engine-failed`) show a localized error notice and do not mutate the source.

6. **Create the translated page only after the result is assembled.** Use `app.pages.addEditorPage("monaco", sourceLanguageId, translatedTitle, translatedContent)` (or the equivalent typed internal `PagesModel` call). Use a localized human-readable target name in `<source title> (<target language>)`, preserve the source language id exactly, and do not copy `filePath`, pipe, encryption state, or source editor state. `addEditorPage` creates a new text host with no file association; nonempty result content is marked modified/unsaved, so it is a new translated document rather than a dirty edit to the source file. Open the page after all batches complete; for selection mode the content is the translated selection only. Keep the source snapshot unchanged throughout.

7. **Localize and wire notices.** Add an English source catalog area, preferably `translation`, in `src/shared/i18n/en/translation.ts`, register it in `src/shared/i18n/en/index.ts`, and use `t("translation.<key>")` for button/menu labels, source/target labels, consent wording, progress/cancel, empty-selection, no-provider, no-language-route, detection/download/translation errors, and partial failures. Keep each sentence whole and use placeholders (for example `{language}`, `{size}`, `{count}`) rather than concatenated fragments. This task adds no user guide; user-facing guide changes are deferred to `/userdoc` at EPIC-135 close.

## Concerns

- The v1 provider's `describe` shape lists model pairs, not an explicit route matrix. This plan derives direct and English-pivot availability from pair descriptors and leaves unsupported-route errors visible; confirm the parallel BT-070 implementation follows the contract's English pivot rule.
- Markdown front matter is not covered by the current Markdown renderer's demonstrated `remark-parse` + GFM pipeline. The implementation must preserve a leading YAML/TOML front-matter block explicitly rather than assuming the parser treats it as opaque.
- In Markdown selection mode, selection endpoints may split inline syntax. Classifying spans against the full document before intersecting the selected range avoids treating an arbitrary partial link or code span as prose. The same protected-span map also keeps code and URLs out of detection samples.
- The output intentionally has no source `filePath` and is modified/unsaved because `addEditorPage(..., content)` routes through `TextFileModel.changeContent()`. Its target-language title and normal dirty marker must make the separation from the source file clear.
- Language codes can include script subtags such as `zh-Hans` and `zh-Hant`; target labels should use readable language names while route matching and the result page's editor language continue to use exact provider/editor ids.
- Epic design proposes translating plain paragraphs/list items, but does not specify an output policy for individual item failures. This plan preserves failed spans verbatim and reports a count so successful translations remain useful without losing text.

## Acceptance Criteria

- A Monaco page with language id `plaintext` or `markdown` shows a Translate toolbar action only when a compatible `text.translate@1` provider is available; other Monaco language ids do not offer v1 translation.
- The toolbar offers selection and whole-page translation; empty selection cannot start selection translation. Right-clicking a nonempty selection in a supported Monaco language shows **Translate selection…** in the Monaco editor context menu only when a compatible provider is available. The action uses group `2_translation`, after Monaco's `1_modification` group and before `9_cutcopypaste`; it is disposed with the editor host. No keyboard shortcut is registered.
- The source dropdown lists detected candidates first, followed by every described `X → en` source plus `en`, with no duplicates. Language names use `Intl.DisplayNames([getActiveLocale()], { type: "language" })` and fall back to codes; `zh-Hans` and `zh-Hant` remain distinct. Detection samples the selection or page according to mode and excludes protected Markdown spans. With no remembered target, default to the UI language if different from source, otherwise English, provided that target is offered. The target picker lists languages derived from `describe`, shows installed routes first, displays missing model sizes for available routes, and remembers the last target.
- A missing model causes an explicit consent prompt before download; download and translation progress are visible and both operations can be cancelled. Contract errors and partial item failures produce localized notices.
- Plain text preserves paragraph breaks, newline style, indentation, and list markers. Markdown translation changes prose and link labels only; fences, indented/fenced code, inline code, URLs/destinations, raw HTML, front matter, and untouched syntax remain intact.
- Requests remain within 32 items / 64,000 code points / 1 MiB serialized message limits; batches preserve source ordering and use the client's four-channel cap.
- Completion opens a new Monaco page with the same language id, translated title, and no source file association. Selection mode opens translated selection only. The source page's content, path, and dirty state are unchanged.
- All new user-visible strings are catalog-backed with `t()`; user guides remain deferred to EPIC-135 `/userdoc`.
