# US-2172: `hover()` applies CSS `:hover`; click hovers first (spike)

**Epic:** [EPIC-208: Input fidelity for web-app tests](../../epics/EPIC-208.md)  
**Proposal:** E3; [US-2138 feedback item 10](../US-2138-web-app-test-feedback/README.md)

Claude verified the live behavior and CSS-forcing path in the dev app; this brief records the workable E3 implementation. Do not implement before review.

## 1. Spike findings

### A. Trusted hover and the actual gap

**Verified in source and in Claude's live run today.** Claude tested a local HTTP lab page in the dev app without touching or moving the user's mouse.

- `src/renderer/automation/mouse.ts::hoverElement()` sends trusted CDP `Input.dispatchMouseEvent` with `type: "mouseMoved"` for the resolved point. It does not use `CSS.forcePseudoState` today. The synthetic option dispatches DOM `mouseenter` / `mouseover` and is a separate behavior.
- The live trusted call `pages["<id>"].editor.hover("#row1")` made `#row1.matches(":hover")` true. `:hover` matched `html`, `body`, `section`, and `#row1`; `.row:hover .menu { opacity: 1 }` applied and remained true seconds later. So trusted input does apply and retain CSS `:hover` in the guest when the user's native pointer is left alone.
- With `.row.vis .menu { visibility: hidden }` and `.row.vis:hover .menu { visibility: visible }`, `click("#menu2")` by itself failed with `Timed out after 2000 ms: Element is not visible.` Calling `hover("#row2")`, then `click("#menu2")` without `force`, succeeded. The live gap is click ordering: `clickElement()` resolves actionability before sending its `mouseMoved`; `resolveActionablePoint()` rejects the hidden target before any input can reveal it.
- `src/renderer/automation/locator.ts` owns `resolveActionablePoint()` and the underlying `ACTIONABILITY_TRANSIENT: Element is not visible.` diagnostic (currently surfaced after the action timeout). `src/renderer/automation/input.ts` contains keyboard definitions/modifier bits, not pointer dispatch. `input-session.ts` maps coordinates/frame offsets. The current pointer dispatch owner is `mouse.ts`.
- `AutomationSurface` delegates shared click/hover behavior to `mouse.ts`. `BrowserTargetModel.cdp()` returns the browser guest's `CdpSession`; `BoardTargetModel.cdp()` returns a `CdpSession` registered to its selected board frame. Both use the same automation surface. `AppTargetModel.id` is `"app"` and targets Persephone's own top-level window.

The browser guide sentence at [`assets/guides/agents/browser-automation.md:24`](../../../assets/guides/agents/browser-automation.md#L24) saying CSS `:hover` does not apply inside browser webviews is wrong as a general statement and must be corrected. A search across `assets/guides/agents/` found this as the only unconditional claim that `:hover` does not apply. **Inference, not reproduced:** a real OS pointer over or moving through the host window may supersede/recompute the guest's synthetic mouse position, so relying on the synthetic position is fragile when a user's physical pointer moves. Claude did not move the user's mouse. The upstream input path maps CDP `mouseMoved` to synthetic mouse movement and the rendering engine has guards for active page, cursor visibility, and known position; those sources describe plausible conditions but do not prove the real-pointer issue in this app ([input dispatch](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/browser/devtools/protocol/input_handler.cc), [hover recomputation](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/core/input/mouse_event_manager.cc)). The forced state is needed to make the desired hover stable against that real-pointer interaction, not because the guest never receives native hover.

### B. CSS pseudo-state live result and node-ID hazard

**Verified in the live guest.** Claude sent `DOM.enable`, `CSS.enable`, `DOM.getDocument({ depth: 0 })`, resolved the row to a Runtime `objectId`, converted it with `DOM.requestNode({ objectId })`, then applied `CSS.forcePseudoState({ nodeId, forcedPseudoClasses: ["hover"] })`. The row matched `:hover`, the menu became visible, and the forced style remained after 300 ms. Sending an empty `forcedPseudoClasses` list cleared it. The complete sequence took about 5 ms. The protocol describes this command as forcing pseudo classes on a node during style computation ([CSS.forcePseudoState](https://chromedevtools.github.io/devtools-protocol/tot/CSS/#method-forcePseudoState), [DOM commands](https://chromedevtools.github.io/devtools-protocol/tot/DOM/)).

A second `DOM.getDocument` invalidates frontend node IDs. Clearing via the old ID then fails `Could not find node with given id`, while the forced style remains applied: computed visibility is still `visible` although `matches(":hover")` reports false. The live run issued `DOM.disable` only after those node IDs had already been invalidated, so it does not establish whether `DOM.disable` clears forced state. Other automation features (`snapshot.ts` and `forms.ts`) use the DOM domain. `CSS.disable` clears all forced pseudo states in that CDP session and restores hidden visibility. Re-resolution with fresh node IDs after another `DOM.getDocument` works. Electron documents that opening DevTools detaches an attached `webContents.debugger`; the app's `CdpTarget` also resets attachment and enabled-domain tracking on its detach event ([debugger detach](https://www.electronjs.org/docs/latest/api/debugger#event-detach)).

**Implementation consequence:** never retain `nodeId`s for later cleanup. Resolve a target and composed ancestors to temporary node IDs, force them, release the Runtime objects, and clear the active session with `CSS.disable` (tolerating detach/already-disabled errors). Do not call `DOM.disable`: the live result is inconclusive, and other automation features use the DOM domain. Navigation creates a new document without the old forced state, so no navigation-specific node cleanup is needed. DevTools opening detaches Electron's attached debugger; commands on a detached/reattached session must tolerate that transition and enable CSS for each fresh force operation.

The source path is already available: selector resolution can return a Runtime object ID via `evaluateCandidateObject()` in `selector-execution.ts`; refs resolve through `resolveRef()` and carry an OOPIF session via `getRefSessionId()` in `ref.ts`. Walk the resolved node's `parentElement` chain and cross a shadow root through its `host`, convert each remote node with `DOM.requestNode`, and force `hover` on the target plus each composed ancestor. For refs, send DOM/CSS commands in that ref's own session. Main-frame selectors use the main session; OOPIF refs are supported by the existing snapshot/ref session map. A selector string does not independently resolve inside an OOPIF; use an iframe ref there. Board commands likewise go through the selected board frame's CDP session.

### C. CDP event traffic and cost

`CdpTarget` installs a `webContents.debugger` `message` listener only while its main-process subscribers exist, then fans each received CDP event to those subscribers. It does not forward every CDP event to the renderer. The `cdpSend` IPC handler is request/reply: it returns the result of `debugger.sendCommand()` and has no generic event-forwarding path. Existing subscribers in `src/main/cdp/` filter for their own event names. Thus enabling CSS does not flood renderer IPC, though `CSS.styleSheetAdded` and other CDP events can reach the main dispatcher while subscribed and incur main-process fan-out. The repository has no general renderer CDP event stream.

Keep CSS enabled only while forced hover is active. On the next pointer action, call the shared clear helper, which uses `CSS.disable` to clear all pseudo states and stop CSS-domain events. Then re-enable DOM/CSS only if that action needs to force hover. The explicit DOM/CSS enable, document lookup, Runtime-to-node conversion, and per-node force calls are the work; Claude measured the force/clear probe at about 5 ms on the lab page. No heavy-page event-rate benchmark was run, so do not leave CSS enabled while idle.

`src/main/cdp/CdpTarget.ts::enableDomain()` tracks only Page, Runtime, and Network; DOM/CSS enablement must be scoped to this helper's own short forced-state lifecycle. The browser guest's F12 path calls `webContents.openDevTools()`; Electron's debugger detach event resets CdpTarget's attachment/domain tracking. DevTools and app automation therefore do not share a persistent CSS session. The app's current browser input path remains the existing `CdpSession` → browser IPC → `webContents.debugger.sendCommand()` route.
## 2. Goal

Keep the already-working trusted `mouseMoved` hover and make it durable with forced CSS `:hover` on browser/board guests. Make `click()` auto-hover only after an actionability check reports the target is not visible, then retry actionability within the existing timeout. Preserve the exact visibility hint for targets that remain hidden.

## 4. Implementation Plan

1. **Own pseudo-state management in one renderer collaborator.** Add `src/renderer/automation/hover-pseudo-state.ts`. It owns session-keyed forced-hover lifecycle, `DOM.enable` / `CSS.enable`, object-to-node conversion, composed-ancestor discovery, and clearing. Reuse `evaluateCandidateObject()` from `selector-execution.ts`, `resolveRef()` and `getRefSessionId()` from `ref.ts`, and `CdpSession.send()`. Key active state by `cdp.registrationKey` plus `sessionId`, not by `CdpSession` instance, because target adapters create new wrapper instances. Export one `clearForcedHover(cdp, sessionId)` function; it issues `CSS.disable` only when this collaborator has forced hover in that session, tolerates detach/already-disabled errors, and drops its active marker. It stores no DOM `nodeId`s. No main-process CDP collaborator or IPC is needed: input is dispatched in renderer automation and the existing `CdpSession` already sends arbitrary CDP commands through the typed browser IPC request/reply path.
2. **Force hover after the native move.** In `src/renderer/automation/mouse.ts::hoverElement()`, keep the current trusted `Input.dispatchMouseEvent(mouseMoved)` exactly as it is. For non-synthetic browser and board targets, then resolve the target and its composed ancestors and force `hover` on each. CSS setup sequence: `DOM.enable`, `CSS.enable`, `DOM.getDocument({ depth: 0 })`, then `DOM.requestNode({ objectId })` for the target/ancestor objects, `CSS.forcePseudoState({ nodeId, forcedPseudoClasses: ["hover"] })`, and release temporary Runtime objects. Leave the DOM agent enabled; do not send `DOM.disable`. Keep CSS enabled only while this hover is active; the next pointer action clears through the helper below. For an explicit ref, issue all commands in its own frame session. Main-frame selectors remain main-frame scoped; OOPIF refs work through the existing `ref.ts` session map, while a plain selector does not search inside an OOPIF. Skip all CSS forcing for `target.id === "app"`; explicit synthetic hover retains its current DOM-event-only behavior.
3. **Use one clear-at-action-entry call pattern.** Import and call `clearForcedHover(cdp, sessionId)` at the start of `clickElement()`, `hoverElement()`, `dragElements()`, `clickAtCoordinates()`, and `dragCoordinates()` in `mouse.ts`, using the relevant input/ref session. Future US-2174 `mouseDown`, `mouseMove`, and `mouseUp` call the same helper at their public action entry. The helper is a no-op with no extra CDP call when this collaborator has no active forced hover. A click's own reveal-and-click sequence does not clear its newly forced state between move/press/release. `CSS.disable` clears all forced pseudo states in that CDP session; never attempt to clear by saved node IDs. A new document has no prior forced state; the next helper call may harmlessly clear the session if its active marker remains.
4. **Make click hover-first only after hidden actionability.** Add `hoverFirst?: boolean` to shared `IBrowserClickOptions` in `src/renderer/api/types/browser-editor.d.ts`, default `true`; `{ hoverFirst: false }` suppresses the reveal attempt and preserves today's no-auto-hover actionability behavior (the shared pointer lifecycle still clears any prior forced state at action entry). In `clickElement()`, pass the click policy into `resolveActionablePoint()`; its existing retry `catch` is the hook. After recognizing the transient `Element is not visible.` reason and before the existing retry sleep, perform one reveal attempt for a trusted click only when `hoverFirst !== false`, the target is a browser/board guest, and no attempt has yet occurred. If no prior forced hover is active, a visible target adds no auto-hover resolver or CSS-domain calls and no style change. If an earlier `hover()` left forced state active, the required action-entry clear still runs. To find the hidden target that the normal visible/action path omits, call the existing resolver in action mode with `{ force: true }` inside `evaluateCandidateObject()`; that mode retains hidden candidates. Honor `nth` and reject unresolved/ambiguous targets using the current locator rules. For refs use the existing ref-to-object helper and its frame session. Force `hover` on the resolved target and composed ancestors once, then continue the same retry loop and original deadline. If the target becomes visible, the normal stable/enabled/hit-test actionability checks still run before the click. Keep explicit `force: true` meaning unchanged.

   Before:

   ```js
   await page.editor.click("#menu2", { force: true });
   ```

   After:

   ```js
   await page.editor.click("#menu2"); // auto-hover is attempted only after “not visible”
   await page.editor.click("#menu2", { hoverFirst: false }); // preserve today's no-reveal behavior
   ```

5. **Keep the fallback hint in the locator-owned error.** In `src/renderer/automation/locator.ts`, when the target is still not visible after the one reveal attempt, or when `hoverFirst: false` is used, include exactly: **“Element is not visible. If it appears on hover, hover its container first with hover().”** Keep the existing `Timed out after {timeout} ms: ` prefix. The current owner is `locator.ts`; this hint remains useful even though the native hover path works when the real pointer is still.
6. **Describe the option on every applicable facade.** Add the option and its JSDoc to `IBrowserClickOptions` in `src/renderer/api/types/browser-editor.d.ts`; `board-editor.d.ts` and `window.d.ts` already consume this shared type, so update their click method descriptions rather than duplicating the option shape. Update `$help` / member descriptions in `src/renderer/scripting/api-wrapper/BrowserEditorFacade.ts`, `src/renderer/scripting/api-wrapper/BoardEditorFacade.ts` and `board-editor-facade-definitions.ts`, and `src/renderer/scripting/ai-vision/namespaces/window-screen.ts` where they expose the shared click options. Explain that `hoverFirst` defaults true, runs only on a not-visible actionability result, and `false` disables the automatic reveal attempt. Keep app-window descriptions clear that the app target does not force CSS pseudo state.
7. **Correct the user guide and extend the board history.** In `assets/guides/agents/browser-automation.md`, replace the false statement at line 24 with the verified behavior: trusted `hover()` sends native CDP mouse movement and applies CSS `:hover` in browser guests; `click()` checks visibility before moving, so use `hover(container)` first or rely on its default hover-first retry. Do not state as fact that the user's real pointer cannot supersede native hover; that remains unverified. Search all `assets/guides/agents/browser*.md` for duplicate claims and correct them. Extend the existing Bridge 1.62.0 history line created by US-2171 in `assets/guides/agents/boards/bridge-versions.md` with the new `hoverFirst` option and hover pseudo-state behavior. Do not change `src/shared/board-bridge-version.ts` again.
8. **Verify through UI integration (Claude runs).** Add or update a case under `integration-test/tests/browser/` using `.row.vis:hover .menu { visibility: visible }`: `hover(row)` then normal click succeeds; hidden-target click auto-reveals and succeeds; `hoverFirst: false` fails with the exact hint; a visible-target click with no prior forced hover adds no CSS-domain calls/style change; the next pointer action clears forced state; browser and board guest paths both work; `window.screen` remains unchanged; a DOM read that calls `DOM.getDocument` between force and clear does not leave a stuck state because clear uses `CSS.disable`. No unit tests or test harnesses are added; Claude runs the integration suite.

The owner of the new rule is `hover-pseudo-state.ts`; `mouse.ts` owns pointer-action sequencing and reuses the existing `resolveActionablePoint()` / dispatch helpers. No protocol code, new correlator, acknowledgement window, error envelope, IPC channel, board rule, import-zone workaround, `await import()`, or roadmap §2.3 god-file growth is planned.

## 5. Concerns

- The live spike tested with the user's physical pointer stationary. The risk that native OS pointer movement later supersedes hover remains an explicitly unverified inference; forced state is planned to make it stable.
- `CSS.disable` clears every forced pseudo state in that CDP session, not one saved node. This is intentional because any later `DOM.getDocument` invalidates node IDs and can otherwise strand a forced style. Centralize forcing/clearing in the one collaborator so no other automation feature owns pseudo state in that session.
- CSS events are not sent to renderer IPC, but the main CDP dispatcher can fan them to existing subscribers while enabled. Keep CSS enabled only during the forced-hover interval, then disable at next pointer action.
- A target still hidden after hover keeps the same timeout prefix and receives the explicit `hover()` hint. Do not bypass other actionability checks or silently force-click.
- No message catalog change is planned: the current locator error is a literal English diagnostic. Epic completion handles deferred review/document/user-guide workflows; implementation work must update the explicitly named browser and bridge guides.
