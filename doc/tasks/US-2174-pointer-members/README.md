# US-2174: Low-level pointer members

**Epic:** [EPIC-208: Input fidelity for web-app tests](../../epics/EPIC-208.md)
**Proposal:** E5; [US-2138 feedback item 17](../US-2138-web-app-test-feedback/README.md)

## Goal

Add trusted `mouseDown`, `mouseMove`, `mouseUp`, and `wheel` members to the shared automation surface so tests can observe pointer gestures while a button remains held and can send wheel input. Track pointer position and held buttons per CDP target, and guarantee release at test cleanup and target teardown.

## Background

### Verified input path and ownership

- `src/renderer/automation/mouse.ts` owns trusted locator and coordinate mouse dispatch. `clickElement()` resolves through `resolveActionablePoint()` (including scroll, stability, visibility, enabled, and hit-test checks), sends `mouseMoved`, then `mousePressed` and `mouseReleased`. `hoverElement()` uses the same resolver and sends one `mouseMoved`. The separate synthetic branches dispatch DOM events and are not trusted input.
- `clickAtCoordinates()` in `mouse.ts` accepts viewport CSS pixels, maps them through `target.inputCdp(...).mapPoint()`, and dispatches trusted events without locator actionability. The browser editor also exposes `clickAt`/`dragTo`; `window.screen` exposes its own app-window coordinate variants. Coordinate space is the selected page/board-frame viewport or app-window renderer viewport, not physical screen pixels.
- `dragElements()` and `dragCoordinates()` share `dispatchDragPoints()`. It validates `steps` as an integer from 1 through 1000 and `holdMs` as a finite value from 0 through 10000 ms. `holdMs` runs after press and before moves; the default is four moves and zero hold. Its `finally` block releases a pressed left button and disables drag interception. That local drag state is not a reusable held-pointer registry.
- Locator actionability lives in `src/renderer/automation/locator.ts::resolveActionablePoint()`. It scrolls into view, checks stability and hit testing, accepts a locator-relative `position`, and routes direct refs to their frame session. Pointer locator members should reuse this resolver with the same options as `hover`; coordinate calls should use `inputCdp().mapPoint()` as `clickAtCoordinates()` does.
- `src/renderer/automation/input-session.ts::createInputSession()` returns a CDP session, optional frame `sessionId`, and `mapPoint()` for same-process ancestor iframe offsets. `src/renderer/automation/CdpSession.ts::registrationKey` is the stable target identity; target adapters create a new `CdpSession` for each operation.
- Keyboard state is currently owned by `src/renderer/automation/input.ts`: `heldKeysByTarget` maps `${registrationKey}|${sessionId}` to key/route entries. `dispatchKeyDown()` registers the route and removes a newly-added entry if dispatch fails; `dispatchKeyUp()` sends the matching route and removes the key in `finally`. `src/renderer/automation/keyboard.ts` routes public `keyDown` and `keyUp` to these functions. **There is no existing automatic held-key release at test end in the inspected source.**
- The test runner's per-page cleanup is `src/test-host/browser-helpers.ts::closePagesOpenedSince()`: its cleanup loop calls hidden `pages[id].editor.releaseFromTestRun` only for `sessionPages` adopted with `ctx.usePage`, then logs the result. Pages opened by the test are closed later, so their input state dies with their CDP targets. `BrowserEditorFacade::releaseFromTestRun()` currently releases test-power adoption only. Neither held keys nor buttons are automatically released today; extend this one cleanup route so adopted-page cleanup releases both.
- Browser right-click policy is already centralized: `clickElement()` and `clickAtCoordinates()` arm `target.automationContextMenu(..., "arm")` before right-button press and release the guard in `finally`. `BrowserTargetModel.automationContextMenu()` excludes popups and delegates to `BrowserEditor.automationMenuGuard`; `BrowserWebviewModel` consumes that guard for the browser menu. Split right-button down/up must retain the guard across the held interval and release it on `mouseUp`, dispatch failure, test cleanup, or target teardown. Page `contextmenu` handlers still receive trusted right-click events; `nativeMenu: true` opts in to Persephone's menu.
- EPIC-208 US-2172 exports `clearForcedHover(...)` for pointer-action cleanup. E5 calls it at one shared entry point in `src/renderer/automation/mouse.ts`, shared by `mouseDown`, `mouseMove`, `mouseUp`, and `wheel`, not from each facade. E5's members do not add US-2173's lost-click check or pre-press settle; they expose the caller-controlled sequence directly.

### Current public surfaces

- `src/renderer/scripting/api-wrapper/AutomationSurface.ts` is the shared delegate used by browser editor, board editor, and `window.screen`. It wraps public calls in `run()` / `runHostOperation()` for readiness and activity handling. It already delegates click, hover, clickAt, dragTo, drag, keyDown, and keyUp to the shared automation modules.
- Browser-page signatures and option types are in `src/renderer/api/types/browser-editor.d.ts`; members delegate from `src/renderer/scripting/api-wrapper/BrowserEditorFacade.ts`. Static `$help` metadata is in `src/renderer/scripting/ai-vision/browser-automation-members.ts` plus `BROWSER_EDITOR_MEMBERS` and `BROWSER_EDITOR_HELP` in `BrowserEditorFacade.ts`.
- Board pages use a separate `BoardEditorFacade` and `src/renderer/api/types/board-editor.d.ts`. Their board-call member metadata and help text are in `src/renderer/scripting/api-wrapper/board-editor-facade-definitions.ts`. The board facade uses the same `AutomationSurface` and `BoardTargetModel` routes input through a per-frame `registrationKey`.
- `window.screen` is implemented in `src/renderer/api/window-screen.ts`, declared in `src/renderer/api/types/window.d.ts`, and described by `WINDOW_COORDINATE_MEMBERS` plus `WINDOW_SCREEN_HELP` in `src/renderer/scripting/ai-vision/namespaces/window-screen.ts`. The namespace spreads `BROWSER_AUTOMATION_MEMBERS`, so common member descriptions must describe selected-target coordinates without incorrectly implying browser-only behavior.
- Recommendation: expose all four members on `window.screen` too. The app target already uses the shared `AutomationSurface`; these calls make trusted low-level input consistent across browser pages, board frames, and the app window. For `window.screen`, `{ x, y }` uses app-window renderer viewport CSS pixels and there is no `tabId`; locator targets use the app document. Preserve `window.screen`'s existing access restriction.
- `src/renderer/scripting/ai-vision/browser-automation-members.ts` is the shared metadata source for browser-like automation members and is also spread into the `window.screen` descriptor. Update static metadata and facade help alongside types and delegates so `$help` and `$describe` match callable methods.

## Implementation Plan

### 1. Own pointer state and trusted dispatch in the automation layer

1. In `src/renderer/automation/input.ts`, add per-target pointer state beside `heldKeysByTarget`, keyed by the same `${cdp.registrationKey}|${sessionId ?? ""}` route. Track the latest mapped page point and held button set/bitmask. Store enough route information to release the same CDP frame/session. Do not key by `CdpSession` object because adapters construct a fresh object for each action.
2. In `src/renderer/automation/mouse.ts`, add shared `mouseDown`, `mouseMove`, `mouseUp`, and `wheel` operations (or extract one-job pointer state/dispatch helpers from `mouse.ts` if necessary to keep it small). All trusted events go through the existing `CdpSession.send("Input.dispatchMouseEvent", ...)`; use CDP `mouseWheel` with `deltaX` / `deltaY`, modifiers, and coordinates. `wheel({ deltaX, deltaY }, target?)` uses the last tracked pointer point when `target` is omitted, otherwise resolves/maps the target point and updates pointer position.
3. Accept a locator plus `position` or `{ x, y }` page viewport coordinates for down/move/up. Use `resolveElementLocator()` and `resolveActionablePoint()` for locator targets, preserving `hover()`'s scroll, stable geometry, hit-test, `force`, `nth`, `timeout`, and frame-ref behavior. Coordinates match `clickAtCoordinates()` and are viewport CSS pixels mapped by `inputCdp().mapPoint()`. `mouseMove` accepts `steps` (default one; validate as a positive integer, capped at 1000, matching drag's existing ceiling) and emits intermediate `mouseMoved` events from the tracked current point to the resolved endpoint.
4. Define `button?: "left" | "right" | "middle"` and `modifiers?: ("Alt" | "Control" | "Meta" | "Shift")[]` on down/up; default button is left. `mouseDown` first sends `mouseMoved` to the resolved point with the pre-existing button mask, then adds the chosen button and sends `mousePressed` with that button and complete bitmask. Compute the CDP `buttons` bitmask from all currently held buttons on every `mouseMoved`, setting `button: "none"` on move events. `mouseUp` sends `mouseReleased` with the selected button and post-release bitmask, then removes it. This is required for page `mousemove` handlers to observe `event.buttons & 1` during a held drag. Release only the selected button so multiple-button state remains coherent. If `mouseDown` is called for a button already recorded as held on that route, first send a best-effort release at its stored point, then clear that stale entry and proceed with the new move/press. A successful reset does not throw solely because the registry was stale; if the release fails for a reason other than target/context loss, fail clearly with `Could not release the previously held mouse button before mouseDown.` and do not send the new press. If it fails with target/context loss, clear the route and let the new dispatch determine whether the target remains usable. This makes repeated down calls recover state left behind by interrupted callers.
5. Guard state transitions: register position/button state only after successful dispatch (or roll back on error); preserve held state on a failed release so cleanup can retry. Keep a right-button menu guard armed from `mouseDown` through the matching `mouseUp`, and release it in failure/cleanup paths. Reuse the existing `automationContextMenu` hook and its `nativeMenu` opt-in semantics; do not duplicate the A5 menu policy.
6. Public signatures are fixed as `mouseDown(target, options?)`, `mouseMove(target, options?)`, `mouseUp(target?, options?)`, and `wheel({ deltaX, deltaY }, target?, options?)`. `target` is `IBrowserElementLocator | IBrowserMousePosition`; `mouseDown` and `mouseMove` require it. `mouseUp` always requires the selected button to be held on that registration/session route; otherwise it fails with `No mouse button is held for this target.` When `target` is omitted, require the held button's tracked point and release there; if it is missing, fail with `Cannot release a held mouse button: no pointer position is tracked for this target.` When a target is supplied, resolve it and move there with the current button mask before release, so the target supplies the release position. `mouseMove` without a prior down remains a normal move with `buttons: 0`. `mouseMove.options.steps` defaults to 1 and counts dispatched move events; when a start point exists, interpolate from it, and when no start point exists, a single direct move is allowed but `steps > 1` fails clearly because no interpolation origin exists. `position` applies only to locator targets. `button` applies to `mouseDown`/`mouseUp`; `mouseMoved` sets CDP `button: "none"` and derives `buttons` from the tracked held set. `nativeMenu` applies to right-button `mouseDown` and remains recorded until release.
7. At the single shared pointer-action entry point in `src/renderer/automation/mouse.ts`, call US-2172's exported `clearForcedHover(...)` before each new public pointer action. The current action must not clear its own state between move/down/up dispatch steps. Keep exactly this one hook call site in the automation layer, not one call per member or facade.

### 2. Wheel semantics and pointer cleanup

1. `wheel({ deltaX, deltaY }, target?)` accepts finite deltas and an optional locator or coordinate target. When omitted, use the current pointer position for that same registration key and frame session; if no position has been established, fail with `No pointer position is tracked for this target.` Validate deltas before dispatch. CDP `Input.dispatchMouseEvent` identifies `mouseWheel` as a mouse event delivered to the page and defines both deltas in CSS pixels; pass them unchanged. This is the CDP-trusted input path, but verify on the pinned runtime with a live page listener that `event.isTrusted === true`, observed `deltaX`/`deltaY` match the requested values, and a scrollable list responds. The PDL also defines page viewport coordinates in CSS pixels. [Chromium's canonical protocol definition](https://chromium.googlesource.com/chromium/src/+/096cd3af2b8ca8fec97a0185e8e802d3e15278b1/third_party/blink/public/devtools_protocol/browser_protocol.pdl) is the reference. Actual scroll distance may vary with page zoom and input handling.
2. Add one exported helper in `src/renderer/automation/input.ts` that accepts the browser editor's registration keys and releases both entries in `heldKeysByTarget` and held pointer buttons, using each stored route/session and pointer position. It calls existing `dispatchKeyUp()` for keys so modifier masks and Electron-vs-CDP routing are preserved, and dispatches mouse-up events through `Input.dispatchMouseEvent`; it removes state on successful release. Update the shared `dispatchMouseEvent()` owner in `src/renderer/automation/mouse.ts` so any mouse dispatch that fails with `isAutomationContextLoss()` drops that route's pointer state. If a key dispatch fails with that classifier, clear the matching held-key and pointer route too. The cleanup helper also treats this target-loss error as state removal and propagates other cleanup failures for runner logging. This is runtime cleanup, not a new protocol.
3. Extend the existing hidden `releaseFromTestRun()` route in `src/renderer/scripting/api-wrapper/BrowserEditorFacade.ts` to make one call to that helper for this editor's browser tab and owned popup registration keys before `testPowerAdoption.release()`. Keep `src/test-host/browser-helpers.ts::closePagesOpenedSince()` as the only runner call site; its existing per-page call applies only to `sessionPages` adopted with `ctx.usePage`. Test-opened pages are closed by the runner, so their target teardown clears their state. Do not add another runner-to-renderer message.
4. Use this cleanup matrix; never add teardown lines to the roadmap §2.3 god files `src/renderer/editors/browser/BrowserWebviewModel.ts` or `src/renderer/editors/board/BoardEditorModel.ts`:

   | Target | Cleanup |
   |---|---|
   | Browser tab | Explicit best-effort release from the non-god owner `BrowserEditor.releaseTab()` and editor `dispose()`; context-loss dispatch also drops state. |
   | Browser popup | Explicit best-effort release in `BrowserPopupModel`'s `popup-closed` handler and `dispose()`; context-loss dispatch also drops state. |
   | Board frame / reload | Use the existing non-god lifecycle seam: `BoardFrameSession.onRetire()` is already subscribed in `src/renderer/editors/board/frame/board-frame-composition.ts`; add held-state cleanup there for that `${boardEditorId}/${tabId}` route. Also self-heal on any dispatch error classified by `isAutomationContextLoss()`. If a later `mouseDown` finds its button still recorded, release-then-press as in step 1. |
   | App window | Renderer teardown naturally discards module state; if the app target/context is lost during a dispatch, `isAutomationContextLoss()` drops the route. A repeated `mouseDown` also self-heals stale held state. |

   Use `src/renderer/automation/context-loss.ts::isAutomationContextLoss()` as the existing classifier. Do not add teardown lines to either god file, or create a new subscription or protocol. The existing `BoardFrameSession.onRetire()` subscription in `board-frame-composition.ts` is the verified board-frame hook.

  ```ts

  await editor.drag("#start", "#end", { steps: 12, holdMs: 100 });

  await editor.mouseDown("#start");

  const committedCount = await editor.count(".selected-day");
  ```

## Concerns

- Source inspection finds no automatic held-key cleanup either: `keyUp` clears explicitly, and current `releaseFromTestRun()` only releases test-power adoption. The planned single input helper releases both tracked key and button state for adopted-page registration keys through that existing runner call.
- CDP's `buttons` bitmask must describe all buttons still held after each transition. A move that omits the bitmask can deliver a `mousemove` while `event.buttons` incorrectly reads zero, defeating the reported calendar/range use case.
- A locator can disappear between resolution and later movement. Re-resolve locator targets for each public action, preserve `resolveActionablePoint()`'s retry/error behavior, and keep coordinate targets tied to the selected viewport and frame session.
- Browser tabs and popups have non-god teardown owners for explicit cleanup. Board-frame cleanup uses the existing `BoardFrameSession.onRetire()` subscription, with target/context-loss dispatch as a fallback; app-window lifetime uses target/context-loss self-healing. In both cases, a duplicate `mouseDown` releases an already-recorded button before pressing again.
- Right-button context-menu suppression currently arms/releases around a one-call click. Split actions need a held guard, including cleanup after failure, while honoring `nativeMenu: true` for browser guests.
- US-2172 exports the `clearForcedHover(...)` hook; the shared entry point calls it once per new pointer action, before actionability/event dispatch.
- Board-call visibility means this task extends US-2171's one-time `1.61.0` → `1.62.0` bridge history entry without another version bump.
