# US-2169: Page-scoped clipboard

## Goal

Give browser tests a page-scoped clipboard facade that captures text the page itself copied or wrote, and lets a test supply text to the page's next clipboard read or paste handler. The host `readText()` never reads the operating system clipboard; browser pages retain their existing permission policy and native clipboard behavior outside an armed test write.

## Background

### Epic decisions and the F5 proposal

- This is EPIC-207 proposal F5 / feedback item 19. [EPIC-207](../../epics/EPIC-207.md) Decisions 1, 2, 3, 7 and 8 bind the design: use a renderer collaborator; add no protocol; gate clipboard test power with `agentMayUseBrowserTestPower`; never read OS clipboard content through this facade; and extend the existing `Bridge 1.61.0` history entry without another version bump.
- Decision 7's `readText()` result must come only from page-side observation of that page's own writes. Reject the tempting main-process `clipboard.readText()` approach even when a preceding copy event appears to establish provenance: it still reads a shared OS resource and cannot prove the text is the page's final payload.
- F5 permits Ctrl+C to retain its current behavior. A real trusted Ctrl+C on a test page continues to perform Chromium's ordinary OS clipboard write; this feature records a page-side observation alongside it and does not intercept, suppress, save, or restore the user's OS clipboard. The app's optional history is independent and is never the source for this API.

### Existing clipboard history is not the live-clipboard API

- `src/renderer/scripting/ai-vision/namespaces/clipboard.ts` implements the `clipboard` node as `ClipboardHistoryNode`. It reads item metadata through `ClipboardHistoryModel.getSnapshot()` and reads stored payload files through `app.fs`; its help explicitly says it never reads the live OS clipboard.
- The opt-in capture path is separate: `src/main/clipboard-service.ts` starts its watcher only when `setClipboardEnabled(true, cap)` enables history. `captureChange()` ignores disabled or excluded changes, then reads Electron's live clipboard to persist payloads and an index under the app data directory. `ClipboardHistoryNode` reads those retained files later. Do not route the browser facade through this service or node.
- `src/main/permission-policy-service.ts` already handles `clipboard-read` for app content and applies the configured permission flow to ordinary browser sessions. Do not change it or widen browser-page permission grants. A page's own `navigator.clipboard.readText()` remains subject to the existing policy; only the test facade's result is guaranteed never to be OS clipboard content.

### Existing browser-test access and init-script paths

- `src/renderer/editors/browser/agent-access.ts` already exports `agentMayUseBrowserTestPower(state)` and the shared `BROWSER_TEST_POWER_REFUSAL`. Reuse both in the clipboard collaborator. The predicate composes `agentMayAccessBrowserPage()` with `openedByAgent || testPowerAdopted`; it preserves the refusal for a user-opened incognito/Tor page.
- `src/renderer/editors/browser/BrowserStorageFacade.ts` is the nearby example for a small nested browser-editor collaborator and shows how a storage namespace performs a page-scoped operation. `src/renderer/scripting/api-wrapper/BrowserEditorFacade.ts` owns nested facade composition, browser-editor descriptors, help text and runner-only members. Do not add clipboard logic to `src/renderer/editors/browser/BrowserWebviewModel.ts`.
- `src/renderer/editors/browser/BrowserTargetModel.ts` resolves the selected tab with `cdp(tabId)`. `src/renderer/automation/CdpSession.ts` already exposes `evaluate()` and `addInitScript()` over the typed `BrowserChannel` invoke/reply path. Use those existing methods; no new IPC channel, request correlator, event channel, error envelope, frame method map, or main-process clipboard feature module is needed.
- US-2165 owns the document-start script registry in `src/main/cdp/cdp-init-scripts.ts`. Register the recorder with `CdpSession.addInitScript()` and also evaluate it in the currently loaded main frame, because adding an init script affects future documents only. `src/renderer/automation/CdpSession.ts` and the registry already own persistence/removal across navigation and debugger detach.
- `src/test-host/browser-helpers.ts` owns `closePagesOpenedSince()`. It already calls `clearInitScripts()` for adopted `sessionPages`, and calls `releaseFromTestRun()` as best-effort cleanup. Extend this existing cleanup path to reset the current-document recorder and remove its own retained script registration; leave the existing generic init-script cleanup intact.

### Recorder and paste feasibility

- The recorder must run in the page's main world. A named isolated world would have separate JavaScript wrappers for `navigator.clipboard` and `DataTransfer.prototype`, so replacing those APIs there would not observe or shape calls made by page scripts in the main world. Use a closure and a non-enumerable page-local handle for host reads/resets; this is obscurity and lifecycle hygiene, not a security boundary. The page under test can inspect or tamper with main-world instrumentation, which is acceptable for test fixtures.
- To observe `copy` and `cut`, the source records selected text as a fallback and wraps main-world `DataTransfer.prototype.setData()` while a clipboard event is active. This captures `text/plain` set by an event handler even when that handler calls `preventDefault()`. Read the final event payload after page listeners have run where available, with the wrapped `setData()` value taking precedence over selection text. Also wrap `navigator.clipboard.writeText()` and `write()` to record successful `text/plain` writes; for `write()`, read only its text/plain Blob. Never read any clipboard API to populate host `readText()`.
- Trusted Ctrl+V cannot be given a replacement `clipboardData` by changing the browser-created paste event after Chromium has obtained the OS clipboard. For an armed test write, intercept trusted Ctrl+V or Shift+Insert at a document-start capture listener, cancel Chromium's OS-backed default paste, consume the staged text, and dispatch a synthetic bubbling/cancelable `ClipboardEvent("paste")` with a constructed `DataTransfer`. The page's paste handlers receive the selected text. If no handler calls `preventDefault()` and the focused target is an editable input, textarea, or contenteditable, follow the synthetic event with `document.execCommand("insertText", false, text)` so Chromium's editing pipeline performs the insertion, including beforeinput/input events, selection replacement, undo behavior, and maxlength handling. The paste event remains untrusted; this does not emulate rich-HTML paste. `navigator.clipboard.readText()` can return a staged test value once without touching the OS. CDP `Input.insertText` is not a substitute for a paste event: it inserts text but does not supply `ClipboardEvent.clipboardData` or exercise paste handlers.
- A recorder registered after a page has already copied cannot recover that earlier copy. `clipboard.arm()` is therefore an explicit idempotent member that installs the recorder in the current document and registers it for later documents; tests arm before the action they intend to observe. `readText()` may ensure the recorder exists for convenience, but returns `null` until an observed page write has occurred.

## Implementation Plan

1. **Add the nested facade and types.** In `src/renderer/api/types/browser-editor.d.ts`, define `IBrowserClipboard` with `arm(): Promise<void>`, `readText(): Promise<string | null>`, and `writeText(text: string): Promise<void>`, and add `clipboard: IBrowserClipboard` to `IBrowserEditor`. In `src/renderer/editors/browser/BrowserClipboardFacade.ts`, own the test-power check, selected-tab recorder lifecycle, `arm`, `readText`, `writeText`, and runner reset. Reuse `agentMayUseBrowserTestPower`, `BROWSER_TEST_POWER_REFUSAL`, `BrowserTargetModel.cdp(tabId)`, and `CdpSession.evaluate()` / `addInitScript()`.

   Before:

   ```js
   await site.evaluate(() => document.execCommand("copy"));
   // The test can dispatch a fake event, but cannot read the page's resulting text safely.
   ```

   After:

   ```js
   await site.clipboard.arm();
   await site.click("button.copy");
   const copied = await site.clipboard.readText();
   await site.clipboard.writeText("pasted by the test");
   await site.pressKey("Control+V");
   ```

2. **Keep page instrumentation and registration state in their owners.** Create `src/renderer/editors/browser/page-clipboard-recorder.ts` for the init-script source factory and page-side recorder operations for install, read, one-shot write and reset. Make installation idempotent per document, keep recorder state in a closure, expose only a non-enumerable handle needed by host `evaluate()`, and scope the recorder to the selected main frame. Because each call-tree request creates a new `BrowserEditorFacade` and nested facades are request-scoped, `BrowserClipboardFacade` must not keep registration IDs in instance fields. Instead, own a module-level `WeakMap<BrowserEditor, Map<string, string>>` in `src/renderer/editors/browser/BrowserClipboardFacade.ts`, keyed by the browser editor model and then tab ID. Use `addInitScript(source)` for future documents and `evaluate(source)` for the current document; all later facade instances for the same model/tab read the ID from this registry. Clear each tab's entry from the existing `BrowserEditor.releaseTab(tabId)` lifecycle hook, which `BrowserTabsModel.closeTab()`, `closeOtherTabs()` and `closeTabsBelow()` already use, and remove its init-script registration best-effort before guest release. Do not add a recorder to an isolated world, shared extension runtime, `src/main/clipboard-service.ts`, or `BrowserWebviewModel.ts`.

3. **Capture only page-produced text.** The page-side `copy`/`cut` hooks record `text/plain` set through the event's `clipboardData` and fall back to selection text when the page leaves the default action in place. The clipboard API wrappers record `writeText()` and `write([{ "text/plain": Blob }])` payloads only after their original promises succeed. `readText()` queries the recorder through `CdpSession.evaluate()` and returns `null` when no page-side write was observed. It must never call Electron `clipboard.readText()`, the clipboard-history service/node, `navigator.clipboard.readText()` or any OS clipboard IPC. Keep ordinary page Ctrl+C behavior unchanged so the trusted operation still writes the OS clipboard as Chromium does today.

4. **Make `writeText()` page-scoped and one-shot.** Validate the argument as a string, stage it in the recorder, and let the next page `navigator.clipboard.readText()` consume it without invoking the native implementation. The document-start capture listener handles trusted Ctrl+V and Windows Shift+Insert only when test text is staged. With no staged text it returns immediately without preventing the key, changing state, or dispatching events, preserving normal page behavior. When armed, cancel Chromium's OS-backed default paste and dispatch a synthetic bubbling/cancelable `paste` event with a constructed `DataTransfer` containing `text/plain`. If no page listener called `preventDefault()` and the focused target is an editable input, textarea, or contenteditable, call `document.execCommand("insertText", false, text)` after dispatch so Chromium's editing pipeline inserts the text and emits its normal editing events. Consume the staged paste once. Do not modify `clipboardData` on the trusted event, use CDP `Input.insertText` as if it were paste, or write to Electron/system clipboard. The event remains untrusted and rich-HTML paste is not emulated. Context-menu and Electron-menu Paste are not intercepted and continue to use the OS clipboard as today.

5. **Compose without protocol or bridge expansion.** In `src/renderer/scripting/api-wrapper/BrowserEditorFacade.ts`, construct `BrowserClipboardFacade`, expose it as nested `clipboard`, add typed member/help descriptors, and add a hidden runner-only `clearClipboardForTestRun()` member that resets the current page recorder and removes its init-script ID using the module-level per-model/per-tab registry. In `src/renderer/editors/browser/BrowserEditor.ts`, call the clipboard collaborator's exported tab-release cleanup from `releaseTab(tabId)` so the registry entry is deleted for every tab close path and its registered init script is removed best-effort. Reuse the existing facade/call tree and existing `CdpSession`; change no files under `src/ipc/`, `src/main/`, `src/shared/board/`, board registries, `BOARD_BRIDGE_VERSION`, or `src/main/permission-policy-service.ts`. Since the epic's `1.61.0` bump already made browser-editor members board-callable, extend that history paragraph rather than bumping again.

6. **Enforce test-power access and clean adopted pages.** Every public clipboard member and the runner reset member call `agentMayUseBrowserTestPower()` before page operations. In `src/test-host/browser-helpers.ts`, extend the `sessionPages` loop in `closePagesOpenedSince()` to call `pages[pageId].editor.clearClipboardForTestRun` before its existing `clearInitScripts` and adoption release calls. Log only action, page ID, success and counts; continue cleanup after failures. The existing US-2165 cleanup already clears all document-start registrations from adopted pages, and owned pages close normally.

7. **Keep copied content out of diagnostics.** In `src/test-host/storage-state-redaction.ts`, add these exact trailing-member matches after the existing `windows[...]` / `pages[...]` prefix stripping in `sensitiveMemberKind()`: `.editor.clipboard.readText` → `clipboard-read`, `.editor.clipboard.writeText` → `clipboard-write`, and `.editor.clearClipboardForTestRun` → `clipboard-reset`. Extend `SensitiveMemberKind` with those three values; `clipboard-read` summarizes returned text by length/count, `clipboard-write` redacts arguments, and `clipboard-reset` redacts errors/results. Reuse the current path-aware redaction flow in `src/test-host/step-format.ts`, `test-log.ts`, `context-operations.ts`, `client.ts`, `results.ts`, and `failure-bundle.ts`. Update `src/renderer/api/mcp/request-log.ts` to classify the same three trailing member paths before retaining calls. Do not log recorder values, clipboard arguments, page clipboard payloads, or errors that can contain them.

8. **Update the existing implementation guides when implemented.** Extend the current `Bridge 1.61.0` paragraph in `assets/guides/agents/boards/bridge-versions.md` with `clipboard.arm/readText/writeText`, emphasizing that no bridge version bump is made. Update `assets/guides/agents/browser-automation.md` to replace the current Ctrl+C/V clipboard statement with the unchanged trusted Ctrl+C behavior, page-side `readText()` privacy boundary, and test-write paste limits: Ctrl+V and Windows Shift+Insert are intercepted only when text is staged; context-menu and Electron-menu Paste continue to use the OS clipboard. Also update `assets/guides/agents/browser.md`, `assets/guides/agents/web-app-tests/index.md`, `assets/guides/agents/web-app-tests/call-boundary-and-examples.md`, and `assets/guides/agents/web-app-tests/attached-runs-and-results.md` with the API, arm-before-action use, test-power eligibility, synthetic event and `insertText` behavior, paste-key coverage, menu-paste behavior, and adopted-page cleanup.

## Concerns

- **The host result is intentionally narrower than the page clipboard.** It reports page-observed text/plain only. It does not capture HTML/images/files, OS clipboard changes from other processes, or page copy activity before the recorder was armed. The method returns `null` before any observed text write.
- **Main-world instrumentation is tamperable.** A page can replace the wrappers, remove listeners, inspect the non-enumerable handle, or fabricate writes. That is acceptable for controlled test pages; this feature is not a security or provenance sandbox. The gate prevents accidental use on pages outside the test-power rule.
- **Paste fidelity and interception are bounded.** The constructed paste event is untrusted. If no page listener cancels it and the focused target is an editable input, textarea, or contenteditable, `document.execCommand("insertText", false, text)` emulates Chromium editing insertion, including beforeinput/input events, selection replacement, undo behavior, and maxlength handling. Rich-HTML paste is not emulated. Only trusted Ctrl+V and Windows Shift+Insert keydowns are intercepted while test text is staged; context-menu Paste and Electron-menu Paste are not intercepted and continue to read the OS clipboard as today. Tests requiring a trusted paste event or rich-HTML behavior need a separate input-fidelity feature.
- **Unarmed key behavior stays native.** The document-start capture listener ignores Ctrl+V and Shift+Insert keydowns while no staged test text exists: no preventDefault, state change, or synthetic event occurs, so ordinary page paste behavior is unchanged.
- **Trusted Ctrl+C still changes the OS clipboard.** This preserves current behavior for attached runs. The new facade does not save/restore the prior contents. The optional clipboard-history feature may independently capture eligible copies when enabled, but this task neither reads from nor routes through that history.
- **Permission policy remains unchanged.** A site's own call to `navigator.clipboard.readText()` continues through existing permission handling. The test facade's `readText()` reads only its recorder and does not grant the page new clipboard-read permission.
- **Lifecycle is page and run scoped.** The init script applies to later documents of the selected browser tab. `clearClipboardForTestRun()` resets the current document; `clearInitScripts()` removes remaining registrations from adopted pages at runner cleanup. Recorder state is per document and is recreated by the init script on navigation.
- **Facade objects are request-scoped.** `BrowserClipboardFacade` instances do not retain init-script IDs. The module-level `WeakMap<BrowserEditor, Map<tabId, initScriptId>>` owns those IDs across call-tree requests, and the `BrowserEditor.releaseTab(tabId)` hook clears the tab entry and removes its registration when `BrowserTabsModel` closes that tab.

## Acceptance Criteria

- `pages[id].editor.clipboard` is a nested page facade with `arm()`, `readText()` and `writeText(text)`; `readText()` returns captured text or `null` when no text was observed.
- `arm()` captures a later trusted Ctrl+C, `document.execCommand("copy")` when Chromium dispatches its copy event, a copy handler's `clipboardData.setData("text/plain", ...)` even if it calls `preventDefault()`, and successful `navigator.clipboard.writeText()` / `write()` text/plain payloads.
- The recorder is installed in the current page and at document start for subsequent documents; a recorder first installed after a copy does not claim to recover that earlier payload.
- Because browser-editor facades and nested namespaces are recreated per call-tree request, the init-script ID is retained in a module-level `WeakMap` keyed by `BrowserEditor` with an inner tab-ID map; a later request can reset/remove the same registration. The existing `BrowserEditor.releaseTab(tabId)` hook clears that entry and removes the registration on `closeTab()`, `closeOtherTabs()` and `closeTabsBelow()`.
- Host `readText()` never calls Electron's OS clipboard API, the app clipboard-history node/service, the page's native clipboard read, or an IPC that returns OS clipboard contents. It cannot return text copied by another app or an unobserved page.
- Trusted Ctrl+C keeps today's Chromium OS clipboard behavior. The task adds no OS clipboard save/restore and makes no change to optional clipboard-history policy.
- `writeText(text)` does not write to the OS clipboard. The next page `navigator.clipboard.readText()` or armed trusted Ctrl+V / Windows Shift+Insert consumes the staged test text once. The keydown path is inert when no text is staged. It dispatches an untrusted synthetic paste event; if no page listener prevents default and the focused target is editable, `document.execCommand("insertText", false, text)` performs native-like text insertion. Rich-HTML paste is not emulated. Context-menu and Electron-menu Paste continue to read the OS clipboard and are not intercepted.
- Public clipboard operations and runner cleanup are gated by the existing `agentMayUseBrowserTestPower()` predicate. User-opened incognito/Tor pages remain refused; `ctx.openBrowser()` and adopted `ctx.usePage()` pages remain eligible.
- `closePagesOpenedSince()` resets the clipboard recorder and clears init-script registrations on adopted session pages, logs only non-content cleanup metadata, and continues cleanup if either operation fails.
- Clipboard payloads and write arguments are absent from runner logs, reports, failure bundles, and the MCP Server Log. The existing app clipboard-history node remains opt-in and is not used by this feature.
- No new protocol code, IPC channels, CDP feature module, board rule, import-zone bypass, or `BrowserWebviewModel.ts` growth is introduced. The existing 1.61.0 bridge history entry is extended with no version bump; `permission-policy-service.ts` is unchanged.
