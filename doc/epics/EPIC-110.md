# EPIC-110: Excalidraw extraction, part 2 — remove `editors/draw` and React

## Status

**Status:** Completed
**Created:** 2026-09-25
**Completed:** 2026-09-25

Roadmap phase: **F, part 2** ([platform-roadmap.md](../platform-roadmap.md) §4 Phase F step 4).
Prerequisites, both cleared: [EPIC-111](EPIC-111.md) (board settings, shipped 2026-09-23) and
[EPIC-112](EPIC-112.md) (board toolbar controls, shipped 2026-09-21). Together they satisfy
[EPIC-109](EPIC-109.md) D11 — *parity before removal*.

## Overview

[EPIC-109](EPIC-109.md) shipped the bundled Excalidraw board and deliberately left the built-in
`draw-view` editor registered beside it as a coexistence fallback. This epic removes the built-in:
`src/renderer/editors/draw/**` (8 files, 1,309 lines), its script facade, its registry and matcher
rows, and then `react`, `react-dom` and `@excalidraw/*` as runtime dependencies. The De-React
programme's last exception closes with it — `ExcalidrawIsland.tsx` is the only `.tsx` file left in
`src/`, and `editors/draw/**` is the only folder eslint exempts from the React import ban.

The epic is mostly deletion, but it is not only deletion. Three things have to be built or moved
first, and each of them is a place where a careless removal loses user data or user state: the
pinned `+`-menu slot, the persisted editor id on every open `.excalidraw` page, and the
*"no image editor is registered"* message that becomes reachable for the first time.

## Goals

- Delete the built-in drawing editor and every seam that names it.
- Leave every existing `.excalidraw` page, and every user's pinned `+`-menu layout, working across
  the upgrade — without asking the user to do anything.
- Take `react`, `react-dom` and `@excalidraw/*` out of the shipped app, and retire the eslint and
  tsconfig machinery that existed only to contain them.
- Make disabling the bundled board with no replacement installed produce a sentence a user can act
  on, which EPIC-109 D6 deferred here because it was unreachable there.

## Non-goals

- **Phase E** (torrent board, audio player) and **US-1474** (ranged streaming into a board provider).
- The **catalog / storefront**, board install flows, or the `permissions`-as-disclosure question
  ([EPIC-109](EPIC-109.md) D8) — untouched, neither extended nor entrenched.
- **Regenerating the board's `lib/`.** EPIC-109 D9 stands: it is generated by hand and committed.
  Nothing here bumps Excalidraw.
- The **same-tab third-party return** defect EPIC-109 recorded (a minted `.invalid` return URL dies
  at DNS before `did-navigate`); it needs `did-fail-load` relayed from `browser-service.ts` and is
  its own task.

## Decisions

**D1 — Migrate persisted state first, delete second, and the migration must not depend on what is
being deleted.**

Two pieces of user state name `draw-view` by string:

- `pinned-editors` — an array of creatable-item ids persisted per user; `draw-view` is in
  `DEFAULT_PINNED_EDITORS` (`tools-editors-registry.ts:53-55`), so essentially every existing user
  has it saved.
- The persisted `editor` field on any open `.excalidraw` page. Session restore resolves it through
  `attachEditorToPage`, which hands the id to `editorRegistry.createEditorSync(targetEditorId, id)`
  (`PagesLifecycleModel.ts:86`). An id that no longer exists in the registry cannot produce an
  editor there — unregistering is not enough, the stored string has to be **rewritten**.

So the rewrite runs on a build where `draw-view` is already gone, which means the migration code
cannot import anything under `editors/draw`, and cannot resolve the replacement by asking the
registry for the old id. It resolves the bundled board the way `getCreatableItems()` does, from
`bundledBoardRegistry` and the board root. The migration must also be a **no-op on a fresh
install** and must not re-fire once it has run — the pattern is already in the codebase as
`boards.excalidraw-library-migrated` (`board-settings-bridge.ts:101-128`), and this epic follows it
rather than inventing a second one.

**D2 — The board inherits `draw-view`'s pinned slot and position, but keeps its own label.**

This is EPIC-109's D3, which *did not survive implementation* and closes here as explicit work.
EPIC-109 predicted the board would take over the "Drawing" row; it did not — the board contributes
its own row, `bundled-board:excalidraw` (`tools-editors-registry.ts:226`), labelled from its
manifest `name` ("Excalidraw"), while the built-in kept its separate, pinned "Drawing" row.

The pin and the position transfer. The **label does not**: the row stays "Excalidraw". Renaming the
manifest to "Drawing" would restore the old string at the cost of lying about what the board is —
it is a replaceable, disableable board named after the library it embeds, and a user who installs a
different drawing board needs the two to be distinguishable. Continuity here is about *where the
button is*, not what it is called.

**D3 — The board's `editorPriority` and capability priorities drop from 60 to 50.**

EPIC-109 D7 raised them to 60 for exactly one reason: the built-in `.excalidraw` matcher claimed
the file at 50. Three rules are distinct here. File resolution keeps the first board on a tie
(`b.priority > best.priority`), and `CustomEditorRegistry.refresh()` puts trusted entries before
bundled entries, so a trusted replacement at 50 wins the bundled board's tie. The safety gate is
the next comparison: after the matcher is deleted, Monaco is the surviving `.excalidraw` built-in
with file-resolution `acceptFile()` floor 0 (distinct from its page `accepts()` value 50), so the
board still wins because 50 > 0. Capability resolution separately sorts by priority, then platform
origin, then registration order; with no platform image/diagram handler, the board declaration wins.
The platform and board capability defaults are both 50. With that row deleted, 60 is not just
unnecessary — it is actively harmful. It leaves an unexplained ceiling that a user-installed
replacement board would have to clear with 61, so `board-manifest.json:18-19,23` all move to 50.

**D4 — `react`, `react-dom` and `@excalidraw/*` move to `devDependencies`. They are not removed.**

The roadmap (§4 Phase F step 4) says they "leave `package.json`". They cannot, and this corrects it.
`scripts/build-board-lib.mjs` regenerates the board's vendored library from
`node_modules/@excalidraw/excalidraw` (line 23) and bundles `react`, `react-dom`,
`react-dom/client` and `react/jsx-runtime` into `lib/deps/` (line 418). The board's `lib/` is
committed — 189 files — and no Persephone build rebuilds it (EPIC-109 D9), so those packages are
needed only to regenerate it when Excalidraw is next bumped.

`devDependencies` states that relationship exactly, and it satisfies the roadmap's actual exit
criterion — *the core bundle no longer contains React* — because electron-builder ships
`dependencies` only. `@types/react`, `@types/react-dom` and `eslint-plugin-react-hooks` are already
dev-only and simply go.

**D5 — `app.pages.addDrawPage()` survives unchanged. `pages[i].editor.id === "draw-view"` does not.**

`addDrawPage` already routes through the capability bus — it invokes `image.edit`
(`PagesLifecycleModel.ts:417-425`) rather than naming an editor — so once the board is the only
`image.edit` handler it keeps working with **no call-site change**. Its consumers are unaffected:
`HtmlEditor.ts:134`, `builtin-schemes.ts:216`, the image viewer, SVG, Mermaid and the snip tool.
It keeps its name; renaming it would add an unnecessary third breaking change.

What does break is the *typed editor facade*. `DrawEditorFacade`, `IDrawEditor`
(`api/types/draw-editor.d.ts`) and the `"draw-view"` member of `EditorView`
(`api/types/common.d.ts:42`, `page.d.ts:39`) all go, so a script that narrows
`pages[i].editor.id` to `"draw-view"` stops compiling and a drawing page exposes the board facade
instead. This is the first breaking change to the documented script API in this epic.

The second is D6's published data-image route: `{ editor: "draw-view" }` stops routing when the
route selector moves to the capability id `"image.edit"`. `ILinkNav.target` must document that it
accepts editor IDs or capability IDs and may be set/overridden by Layer 2 resolvers. Both breaks
are `/userdoc`'s to announce at epic close.

**D6 — The `data:image/…` route stops naming an editor id.**

`builtin-schemes.ts:212` special-cases `data.target === "draw-view"` and calls `addDrawPage`. Since
D5 keeps `addDrawPage`, the condition changes to `data.target === "image.edit"` — a capability
request resolved through the same bus that serves the call underneath it. It must not be
re-pointed at the board's editor id, because board editor ids are derived from the board root path
and are therefore not a constant. There is deliberately no `"draw-view"` legacy alias: the
published route breaks rather than keeping the deleted identifier in the runtime.

**D7 — "No image editor is registered" is this epic's one new user-facing behaviour.**

EPIC-109 D6, as amended, deferred it here and the reasoning is unchanged: with `draw-view` gone,
disabling the bundled board with no replacement installed leaves `image.edit` and `diagram.edit`
genuinely unhandled for the first time. The bus already types the rejection, but
`noHandlerError()` (`capabilities.ts:245-247`) produces a developer-shaped string —
*No capability handler matches "image.edit".* The four consumers (image viewer, SVG, Mermaid, snip
tool) need it surfaced as a **state with a remedy**, not as a failure. Shipping it in EPIC-109 would
have been untested code for an unreachable state; shipping it here is the opposite.

**D8 — `drawLibrary.ts` dies here, which is what makes a standing comment in `settings.ts` true.**

EPIC-111 removed `drawing.library-path` from the typed settings union and left `drawLibrary.ts`
compiling through the `settings.get<string>(key)` escape hatch. That escape hatch's doc comment
(`settings.ts:226-235`) records a widening to `any` being proposed **twice** and rejected both
times, on the explicit grounds that it would disable checking codebase-wide *"to serve one file that
EPIC-110 deletes"*. This is that deletion.

What stays: the legacy library-path **migration** in `board-settings-bridge.ts` and its
`boards.excalidraw-library-migrated` bookkeeping key. It reads a settings key, not the editor, and
an upgrading user still has `drawing.library-path` in their `settings.json`. Deleting the editor
does not make their library folder stop existing.

**D9 — Abort boundary: if a real `.excalidraw` page cannot be restored into the board, stop before
the deletion.**

EPIC-109 D11 made feature parity the gate for starting this epic. Data parity is the gate for
finishing it. D1's migration is the riskiest work here and it is sequenced first precisely so that
failing it costs nothing — everything up to that point is revertible, and nothing is deleted until
a page saved by 5.0.3 opens in the board on 5.0.4.

**D10 — The bundled board ships an icon, reusing the built-in's glyph.**

*(Added 2026-09-25, from a user observation during implementation: the Excalidraw board was the
only board in the app without an icon.)*

Boards declare an icon by dropping `icon.svg` / `icon.png` / `icon.ico` in the board folder, probed
in that order by `board-icon-cache.ts:23` and rendered as a plain `<img src>` on the tab, the
main-editor tile and the sidebar row. Every other installed board has one; the bundled Excalidraw
board did not, so it fell back to a generic glyph exactly where D2 says it should read as the
drawing entry.

The glyph is lifted verbatim from `DrawIcon` in `src/renderer/theme/language-icons.ts:207-214` —
the cyan (#4DD0E1) pencil the built-in Drawing editor used — so the board looks like the thing it
replaces in the place it replaces it. `DrawIcon` itself stays in the codebase: it is still the
`*.excalidraw` language icon (`language-icon-resolver.ts:136`) and is used by the HTML, image,
Mermaid and SVG editors' toolbars.

Shipped as `assets/boards/excalidraw/icon.svg`, which `electron-builder.yml` already carries
outside the asar with the rest of the board.

## Exit criteria

1. `src/` contains no `.tsx` file, no import of `react` or `react-dom`, and no folder exempted from
   the React import ban.
2. `react`, `react-dom` and `@excalidraw/*` appear only under `devDependencies`, and
   `npm run build-board-lib` still regenerates the board's `lib/` from them.
3. The production renderer bundle contains no React. Measured, with the before/after numbers
   recorded in US-1509 — not asserted.
4. An `.excalidraw` page left open in 5.0.3 restores into the bundled board on upgrade, with its
   content intact and no error toast.
5. A user whose `pinned-editors` contained `draw-view` sees the board in the same `+`-menu position
   after upgrading, and Tools & Editors shows **one** drawing row, not two (D2).
6. `image.edit` and `diagram.edit` from the image viewer, SVG, Mermaid and the snip tool all land in
   the board.
7. Disabling the bundled board with no replacement installed produces the D7 message from all four
   consumers, and re-enabling restores them with no restart.
8. `npm run typecheck`, `npm run lint` and `npm run build-prod` pass; the app renders.

### 2026-09-25

- Epic created. Investigation found four things the roadmap's step 4 did not anticipate, all folded
  into the decisions above:
  - **`app-asset://excalidraw` serving no longer exists.** Step 4 lists it for deletion; a grep of
    `src/main` and `src/ipc` finds nothing. The board's fonts already ship inside the board, as
    EPIC-109 intended. The roadmap line is stale and `/document` should correct it at close.
  - **The dependencies cannot leave `package.json`** — `build-board-lib.mjs` needs them installed.
    See D4. This is the one place the roadmap is wrong about an outcome rather than a detail.
  - **`addDrawPage` needs no work at all** (D5) — it was already written against the capability bus,
    which is Phase D paying for itself a phase later.
  - **Persisted state names `draw-view` in two places** and `createEditorSync` cannot absorb an
    unknown id (D1). This is the real risk in the epic and it is sequenced first.
- No React plugin is configured in `vite.renderer.config.ts` — JSX comes from tsconfig's
  `"jsx": "react-jsx"` (`tsconfig.json:24`) and esbuild's default. US-1509's build-config surface is
  therefore just that line plus the `@excalidraw/excalidraw/dist/types/*` `paths` entry
  (`tsconfig.json:21`), not a plugin removal.
- `optimizeDeps.entries` and the `**/assets/boards/*/lib/**` watch-ignore in
  `vite.renderer.config.ts` are about the **board's** committed `lib/`, not the built-in editor.
  They stay.
